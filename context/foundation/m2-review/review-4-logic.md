# Review 4 — business logic correctness against PRD v2 (PR #4 @ 163803b)

Scope: `src/lib/events` (dates, noon rule, DST), `floor`, `event-waiters`, `privacy`, `rsvp`, `quiz`, `menu` + `orders/prices*`, `modules` + the middleware/dispatcher gates, `lead`, `templates` (preview vs `apply_venue_template`), `guests/import` + `diets`, the guest and TV poll tokens, `tv-rooms`, `prints`, `reset`, scale limits vs DB CHECKs — plus the migrations they call (`20261110200000`, `20261110220000`, `20261110230000`, `20261111010000`, `20261111020000`, `20261111040000`, `20261111050000`, `20261111060000`).

Most of the anchor logic is sound and consistent between the TypeScript rules and the SQL that mirrors them. The findings below are the places where the code can produce a wrong or destructive outcome for an input the UI/API accepts.

---

## Findings (most severe first)

### [high] A mistyped or back-dated event date silently and irreversibly deletes all guest data on the next request
- Location: `src/pages/api/panel/events/[id].ts:54-72` (PATCH, no date guard), `src/lib/events/service.ts:160-183` (`updateEvent` writes `event_date` unconditionally), `src/lib/auth/service.ts` `findEventMembership` and `src/lib/access/resolve.ts:107-199` (every guard calls `enforceGuestRetention`), `src/lib/privacy/service.ts:85-96`, `supabase/migrations/20261111050000_privacy_retention.sql` `purge_event_guest_data`, `src/components/events/EventCard.tsx:50-70` (`EventDetailsForm` saves the date without any confirm).
- Failure scenario: an upcoming event has 120 imported guests with diets, groups, a published seating, RSVPs. A manager edits the card and types `2025-11-20` instead of `2026-11-20` (or picks a past date for an event entered "for the records"). The PATCH itself passes the guard with the OLD date, then writes the typo. The very next request that opens the event — the island's next re-read, a page reload, the client's `/o/<key>` link, the TV poll (every 2.5 s) or the tablet poll — runs `enforceGuestRetention` → `isGuestDataExpired("2025-11-20", 30, now)` is true → `purge_event_guest_data` deletes every guest, group, snapshot, RSVP answer, guess, quiz answer, per-event waiter and order note, and sets `guest_access_enabled = false`. Fixing the date afterwards restores nothing. The same happens for a NEW event created with a date past the term: guests added through the client link are deleted on the following read (the overnight log accepts the "client link of an already-expired event" case, but not a live event whose date is mistyped).
- Evidence:
  - `updateEvent`: `...(patch.date === undefined ? {} : { event_date: patch.date })` — no check against the restaurant's term or the event's guest data.
  - `resolveAccess` (every link): `await enforceGuestRetention(db, retentionRow(data), now);` before returning the access.
  - `enforceGuestRetention`: `if (!isGuestDataExpired(row.eventDate, row.retentionDays, now)) return null; return purgeEventGuestData(db, row.eventId, now);`
  - `EventDetailsForm.submit` calls `onSave({ name, date, expectedGuests })` with no `window.confirm` (archive, delete and the lead switch all have one).
  - The TV poll (`resolveAccess` tv branch, every 2.5 s) and the tablet poll (restaurant branch, every 15 s) both run `enforceGuestRetention`, so with either screen open the purge lands within seconds of the save — there is no window to notice and fix the typo.
- Fix sketch: in `PATCH /api/panel/events/<id>` (and `POST …/restaurants/<id>/events`) refuse with a 409 (or require an explicit `confirmPurge: true`) when the new date makes `isGuestDataExpired(newDate, retentionDays, now)` true while `event_has_guest_data(id)`; mirror it in `EventDetailsForm` with a confirm that names what will be deleted. Alternatively make `purge_event_guest_data` ignore events whose `event_date` was changed within the last N hours (needs a column) — the route-level refusal is simpler.
- Confidence: high (mechanics verified end to end); whether to treat it as a defect rather than "retention working as designed" is the user's call.
- needs-user-decision: yes

### [low] TV quiz counters go stale when the question list changes during a run
- Location: `supabase/migrations/20261111060000_pub_quiz.sql` `quiz_tv_version` (`r.revision::text || '-' || count(quiz_answer)`), `src/lib/quiz/service.ts:87-111` (`addQuizQuestion`), `:165-193` (`deleteQuizQuestion`), `src/components/tv/TvQuiz.tsx:40,47` (`t.tvQuestions(quiz.total)`, `t.tvQuestionOf(question.number, quiz.total)`).
- Failure scenario: the quiz is on the TV (intro or a closed question). The client adds a 4th question, or deletes an unanswered draft. Neither `addQuizQuestion` nor `deleteQuizQuestion` bumps `quiz_run.revision` and the answer count is unchanged, so the TV's 204 path keeps answering "unchanged" and the screen shows "3 pytania" / "pytanie 2 z 3" until the next `ask`/`close`. (The phones are fine: `quizKey` includes `total` and `closed`, so the guest token changes.) Deleting a closed question with zero answers leaves `closed` stale the same way.
- Evidence: `quiz_tv_version` reads only `r.revision` and `count(*) from quiz_answer`; `addQuizQuestion` is a plain insert; `getTvScreenVersion` compares that string only.
- Fix sketch: include the question count (and closed count) in `quiz_tv_version`, e.g. `revision || '-' || answers || '-' || (select count(*) from quiz_question where event_id = r.event_id) || '-' || closed`, or bump `quiz_run.revision` from a trigger on `quiz_question` insert/delete while a run row exists.
- Confidence: high

### [low] `deleteQuizQuestion` can delete the question that is on the TV (check-then-act race)
- Location: `src/lib/quiz/service.ts:165-193`.
- Failure scenario: the client's page has two tabs (or the staff dispatcher runs in parallel). Tab A reads `quiz_run.question_id` (not this question), tab B runs `ask` for it; A's `delete … where event_id and id` then succeeds. The FK `quiz_run_question_fkey … on delete set null` leaves `phase = 'question'` with `question_id = null`: `quiz_tv_state` answers `question: null` in phase `question`, `close` raises `NO_OPEN_QUESTION`, guests get `QUIZ_CLOSED`, and the TV shows an empty question frame until the client asks the next one. `quiz_run_action` even documents this state ("A question deleted while on the TV leaves phase 'question' without a question").
- Evidence: the service reads `run.question_id` and the row in `Promise.all`, then deletes with no condition tying the delete to the run row; `quiz_run_action` takes `pg_advisory_xact_lock(3013, event)` but the delete does not.
- Fix sketch: a small DB function under the same `(3013, event)` advisory lock that raises `QUESTION_ON_TV` when `quiz_run.question_id = p_question_id` and deletes otherwise; a PostgREST-side filter on the service's earlier read cannot close the window.
- Confidence: medium (small window, but the resulting state is visible and confusing)

### [low] `floorWindowEnd` throws for an event dated 2100-12-31 (an allowed date)
- Location: `src/lib/floor/rules.ts:20-26`, `src/lib/events/dates.ts:143-161` (`localInputToInstant` refuses years > 2100), `src/lib/events/rules.ts:10-11` (`EVENT_DATE_MAX = "2100-12-31"`).
- Failure scenario: an event dated `2100-12-31` (accepted by `parseEventDate`) → `floorWindowEnd` calls `localInputToInstant("2101-01-01T12:00")` → `null` → `throw new Error(...)`. The readout scopes are built in Astro page frontmatter (`src/pages/r/[key].astro:32`, `src/pages/r/[key]/odczyt.astro:19`, `src/pages/panel/obsluga/[id].astro:27`, `src/pages/panel/obsluga/[id]/odczyt.astro:20`, `src/pages/kelner/sala/[id].astro`), so the tablet, both floors and their `/odczyt` pages for that event are a server 500 instead of a page. Absurd date, but the validator admits it and the crash is deterministic.
- Evidence: `const instant = localInputToInstant(`${addDays(eventDate, 1)}T…`); if (instant === null) { throw … }`; `src/lib/offline/staff.ts:90,99,114` call it unconditionally from the page-level scope builders.
- Fix sketch: lower `EVENT_DATE_MAX` to `2100-12-30`, or let `localInputToInstant` accept year 2101 (`year > 2101`).
- Confidence: high

### [low] Template preview and `apply_venue_template` lower-case names with different algorithms
- Location: `src/lib/templates/rules.ts:46-48` (`venueNameKey = name.toLowerCase()`), `supabase/migrations/20261110200000_venue_templates.sql` `apply_venue_template` (`lower(name)`), and the rest of the app uses `displayNameKey` = `toLocaleLowerCase("pl")`.
- Failure scenario: a table or room whose name contains a letter where JS `String.prototype.toLowerCase` and Postgres `lower()` (libc collation) disagree (dotted capital İ U+0130, a few Greek/Georgian cases): the preview (`templateUpdatePreview`) reports the table as removed+added and lists its occupants under `lost`, while the apply matches it in place and keeps the seats (or vice versa) — breaking the "the preview names exactly who the apply unseats" invariant that the confirm relies on. Also inconsistent with `displayNameKey` used everywhere else for the same unique index.
- Evidence: `export function venueNameKey(name: string): string { return name.toLowerCase(); }` vs `where event_id = p_event_id and lower(name) = lower(v_table.name)`.
- Fix sketch: use `displayNameKey` (or `toLocaleLowerCase("pl")`) in `venueNameKey`; the realistic Polish alphabet is identical under both, so this is a hardening, not a Polish-venue bug.
- Confidence: medium (requires exotic letters)

## Observations that are NOT defects but worth knowing (deliberate decisions, verified)

- Price rule "event price wins over the catalog": a name priced 0 before the menu stays 0 for new lines until „Cennik wydarzenia” — logged as an accepted observation in S-16; the code does exactly that (`newestPriceFor(lines, name, null, item?.priceGrosze ?? 0)`).
- `quiz_tv_version` includes the event's total answer count, so every guest answer makes every TV poll re-fetch the full `TvScreenDto` (~10 KB with 150 names) — load, not correctness.
- RSVP: un-marking an absence on the guest list turns a guest's own "no" into "coming (by organizer)" with no dish — a consequence of the single source of truth (`attendanceOf`), logged in the S-25 decisions.
- `seating/restore` and `seating/history` are not gated by `seatingDraw` (only `seating/draft` is); CLAUDE.md documents the history exemption, restore is a manual-seating action.

## Checked and fine

- **Dates / time zone**: `localDateTime`/`platformToday`/`eventTiming` use `Intl` in Europe/Warsaw (`hour % 24` guards the "24" quirk); the noon rule (yesterday's event is "today" until 12:00) matches `isFloorOpen`, `canAddWaiter`, `add_event_waiter` (`v_expires <= now()` at `((date+1) + 12:00) at time zone 'Europe/Warsaw'`) and `floorWindowEnd` at the exact boundary. `localInputToInstant` resolves the spring gap to the instant after it and the autumn repeat to the later (CET) instant, as documented; `addDays`/`defaultDeadlineInput` do calendar arithmetic in UTC only. No `toISOString().slice(0,10)` of `new Date()` or server-local getters anywhere server-side (`readout.ts` getters run in the browser by design). `event_date` default and `guest_data_expired` are Warsaw dates in SQL.
- **Retention term edges**: app `platformToday(now) > eventDate + N` ≡ SQL `event_date + N < (p_now at time zone 'Europe/Warsaw')::date`; with N ≥ 1 never inside the floor window. `purge_event_guest_data` re-checks under the row lock, is idempotent (`clean` fast path), never touches templates; cascades cover RSVP answers, guesses, quiz answers/scores, seat assignments, keys. Guest keys of a purged event get the identical denial (`purge.status !== "kept"` → null). `findMemberEvent` keeps the export away from support mode.
- **Per-event waiter**: `parseWaiterCode` (case/space/dash tolerant, id must be separated), one-time consume as a single conditional UPDATE, throttle per waiter id, `waiterStatus` vs `.gt("expires_at", now)` consistent, `findWaiterFloorEvent` re-reads event/restaurant/window on every request.
- **RSVP**: deadline typed in Warsaw time → instant; `open` is `now < deadline` in both the app and `guest_rsvp_state`/`save_guest_rsvp`; `close_event_rsvp` = `least(app, db)`; `save_guest_rsvp` locks the event `FOR SHARE`, writes `is_absent` first then the answer, so the author survives the `guest_rsvp_absence_by_organizer` trigger; options resolved only among AVAILABLE menu items (`full`/`reduced`/`off` in SQL mirrors `availableItems`); withdrawn options keep counting with `offered: false`; counts partition every guest into exactly one bucket; `attendanceOf`/`byOrganizerOf` are the single derivation everywhere (phone, board, export).
- **Quiz**: `parseQuizQuestion` ↔ `quiz_options_valid` + `quiz_question_correct_in_range`; `quiz_run_action` phases (start/ask/close/results/end) with the `(3013, event)` lock, `QUESTION_OPEN` guards, `end` closes an open question; `save_quiz_answer` accepts only the event's open question under `FOR SHARE` (cross-event ids → the same `QUIZ_CLOSED`); competition ranking: `rankQuiz` ↔ `rank() over (order by points desc)`; TV names only at `results`, places ≤ 3 cut in SQL and in `tvQuizResults`; the correct option/counts only at `reveal`; the phone's `result` is null for a non-player. Composite FKs keep answers/scores/run inside one event.
- **Menu + prices**: menu active ⇔ `getAvailableMenu` non-empty; `POST /orders` and a rename to ANOTHER dish are gated (spelling fix and other edits are not, as specified); the floor refill runs the same handler (venue prices, `price` in the body → strict 400); `priceForNewLine`/`priceAfterRename` implement "newest event price, else menu price, else 0"; drinks seed from the `drinks` course only when the bill has no line of that name; `setEventPrice` reprices every line of the name. Integer grosze throughout (`parseAmount` builds `whole*100 + fraction` from digit strings, no float multiply).
- **Modules**: `effectiveModules` = available ∧ enabled ∧ (free ∨ unlocked); DB defaults equal `DEFAULT_*` (aiTopics and guessing off, pubQuiz locked); `moduleForApiPath` covers every organizer route of the six modules present in `src/pages/api/o/[key]/**` (`questions*`, `ai-topics`, `guesses*`, `tv-spotlight*`, `seating/draft`, `quiz*`) and every guest route (`questions/draw`, `ai-topics`, `guess`, `quiz`); the middleware gates before the lead rule, the dispatcher gates identically; `set_event_module_unlock` requires a live support grant of THIS session and logs `unlock`/`lock`; `enableProblem` gives `unavailable` before `locked`.
- **Lead rule**: `clientMayWrite`/`staffMayWrite` are exact complements; the middleware refuses every non-safe method under `/api/o/<key>/` (409 `venue-leads`), the dispatcher every staff mutation while the client leads (409 `client-leads`); the floor dispatch bypasses both on purpose; guest/TV/tablet never gated.
- **Templates**: preview and `apply_venue_template` use the same match (name, case-insensitive), the same seat loss (table removed → all; seat_count lowered → seats above, via `unseat_beyond_seat_count`, pins included); rooms are upserted before tables are moved, tables deleted before rooms, so no cascade removes a matched table; locks `(3003, event)` then `(3003, template)`; `create_event_from_template` copies the venue only (modules/menu/brand take defaults, as specified).
- **Import + diets**: BOM stripped, RFC 4180 quotes with embedded line breaks and `""`, separator by the first non-blank line (tab > `;` ≥ `,` > none), header by known PL/EN words else positional, list markers stripped only in the one-column case, every blocking problem reported with its line (missing name, too long, repeat in file, already on the list, unknown diet word, note > 120, > 150 in all, > 1000 rows, nothing to add), save re-parses and is all-or-nothing; `parseDietCell` tries the whole phrase first, then splits on `, ; / + & |` and „i”/„oraz”/„and”; tags normalized to `DIET_TAGS` order; DB CHECKs (`guest_diets_known`, `guest_diets_size ≤ 8`, note 1–120) mirror the constants.
- **Poll tokens**: `getGuestStateVersion` and `getGuestState` read the same five things (`getPublishedVersion`, `getGuestGuess`, `getGuestOrders`, `getGuestRsvp`, `getGuestQuiz` only while `modules.pubQuiz`) and build the token with one function; RSVP and quiz go into the hashed part only when non-null; modules via `guestModulesKey` (`p` appended only when the quiz is on). Worst-case length ≈ 50 of 64. TV: `getTvScreenVersion` and `getTvScreen` pass the same `spotlightOn`/`quizOn` flags from the access and map `null` → undefined identically, so the 4th part appears/disappears on both paths together; `quiz_tv_state.version` is computed by `quiz_tv_version` in the same statement.
- **TV rooms**: readability from `smallestNameFontPx` vs 2.5 % of the screen height, rotation only with ≥ 2 rooms with published tables, pin resolved case-insensitively against the snapshot's rooms (never echoing the raw query), `keepRoomIndex` on republish.
- **Prints**: every print reads the LATEST published snapshot (`getRoomPrintSource` → `getLatestSnapshot`), diets joined live by guest id and only for present guests; board pagination never leaves a letter heading as the last row of a column and marks continued letters; staff list splits long tables across pages and keeps the summary first; place/table card sheet math is pure arithmetic on A4 minus margins.
- **Reset**: `RESET_PARTS` ↔ `c_order`, implications (`guests` → guesses, aiUsage, seating, quiz; `venue` → seating) identical in TS and SQL; `quiz` part clears answers, scores, run and `asked_at`/`closed_at` but keeps questions; trial reset limited to `guesses | seating | quiz` by a strict schema; every reset hides the TV spotlight.
- **Scale**: `MAX_SEATS` 30 / `MIN_SEATS` 2 ↔ `venue_table_seat_count` and `seating_snapshot_table_seat_count` CHECKs; `MAX_PREDICTED_PLACE` 150 ↔ `guess_predicted_place_range`; `MAX_GUESTS` 150, `MAX_TABLES` 60, `MAX_ROOMS` 10, `MAX_ORDER_ITEMS` 600, `MAX_DRINK_ITEMS` 200, `MAX_MENU_ITEMS` 300, `MAX_QUIZ_QUESTIONS` 50 are app rules (no DB count CHECKs, as documented); `MAX_EVENT_WAITERS` 30 passed as `p_max`.
- **Status unions → HTTP**: RSVP `closed` 409 / `not-offered` 400 / `not-found` 404; quiz `question-open|asked|no-open-question|locked|on-tv` 409, `full` 409, option out of range 400; waiter `closed`/`too-many` 409, name 400; menu/template/event not-found → the identical 404; module `unavailable`/`locked`/`off` 409 with codes. Idempotent paths: `publishSeating` unchanged, `set_event_module_unlock` unchanged, `set_event_rsvp_options`/`set_event_menu` replace-all.
- **Polish ordering**: `Intl.Collator("pl")` (numeric where table names) used consistently for guests, RSVP rows, quiz standings/TV, dish/menu names, board entries; ties in the DB `rank()` are ordered by the app only.
