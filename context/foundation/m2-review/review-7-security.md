## [low] The nightly clean-up stands on an unverified Lambda Web Adapter assumption; if it is wrong, every run fails silently while the privacy texts promise daily deletion

- Location: `scripts/lib/aws-deploy.mjs:183` (`AWS_LWA_PASS_THROUGH_PATH: RETENTION_JOB_PATH`), `src/pages/api/jobs/retention.ts:16-20`, `node_modules/astro/dist/core/app/origin-check.js:9-21`, promises in `src/lib/legal/privacy-policy.ts:110,275` and `src/lib/privacy/messages.ts:13,45,196,239`.
- Failure scenario: EventBridge Scheduler invokes the function with `{ job, token }`; the adapter POSTs the raw event to `/api/jobs/retention`. Astro's built-in origin check (on by default) runs BEFORE the project middleware and refuses any non-safe request that has no `Origin` when it also has no `Content-Type` (`return !isSameOrigin`) or a form-like one. The route only works if the adapter sets `Content-Type: application/json`. The author states this is an assumption that could not be checked without AWS (README line 293). If it is wrong, every night is a 403 from Astro — no app log line, no `support_log`, nothing in CloudWatch beyond the adapter — while the guest notice, the privacy policy draft and the terms now say "a daily automatic clean-up deletes it". A dormant restaurant's guest data (names, diets — GDPR art. 9) then stays in the database indefinitely, exactly the state decision 3 was meant to end, and the texts are wrong.
- Evidence: `origin-check.js`: `const hasContentType = request.headers.has("content-type"); if (hasContentType) {…} return !isSameOrigin;` — `retention.ts:19-20`: "Content-Type application/json, so Astro's origin check lets it through without an Origin" — README 293: "założenie z dokumentacji Lambda Web Adapter, którego nie dało się sprawdzić bez AWS".
- Fix sketch: make the deploy prove it — after `createSchedule`/`updateSchedule`, run `aws lambda invoke --payload fileb://<the schedule's target input>` and fail the deploy unless the answer is the JSON `RetentionJobResultDto` (counts). Alternatively, add a CloudWatch metric filter/alarm on the absence of the "Retencja danych gości" line for 48 h. Until one of these exists, soften the texts to "daily when the schedule is configured" or keep the manual check as a required step. Fails closed (nothing is deleted wrongly), so this is a privacy-promise risk, not a data-exposure one.
- Confidence: medium (cannot be verified offline; the failure mode itself is certain from Astro's code).
- `needs-user-decision: yes` (infrastructure: a live `invoke` in the deploy, or an alarm, or a text change).

## [low] `issue_owner_link` does not refuse an owner account that is itself a platform administrator — one admin can take over a peer admin's account through „Nowy link”

- Location: `supabase/migrations/20261111070000_review_fixes.sql:81-91`; caller `src/lib/platform/service.ts:186-215`; route `src/pages/api/panel/platform/restaurants/[id]/owners/[accountId]/link.ts:23`.
- Failure scenario: admin A opens the platform page of a restaurant whose owner O is also a platform admin (an admin made owner through `add_restaurant_owner`, or the first admin who runs a venue) and clicks „Nowy link”. The function checks only `m.role = 'owner'`, issues a RESET link for O's account (O has a password), A opens it, sets O's password and is logged in AS O — with O's platform-admin flag — and O's sessions end. Every later `support_log` row (enter, access, unlock) snapshots `admin_email = O`. No privilege is gained (A is already admin), but the audit trail the whole admin-support-log slice exists for now names the wrong person, and O is locked out. The team path refuses exactly this case: `team_account_exclusive` returns false for a platform admin (`20261110140000_restaurant_team.sql:80`), so a team's link can never target an admin — the platform's new single writer has no such check. The old TypeScript `issueOwnerLink` had the same gap, so this is pre-existing, but `issue_owner_link` is now the only writer and the natural fix location.
- Evidence: `select a.email, a.password_hash is not null into v_target_email, v_has_password from public.restaurant_member m join public.staff_account a on a.id = m.account_id where m.restaurant_id = p_restaurant_id and m.account_id = p_account_id and m.role = 'owner';` — no `is_platform_admin` condition; then `perform public.issue_staff_token(p_account_id, v_kind, …)`.
- Fix sketch: add `and not a.is_platform_admin` to that `where` (→ `OWNER_NOT_FOUND` → the identical 404), or refuse only the `reset` kind for admins. An admin who lost the password keeps `npm run platform:admin -- <email> --remote` (operator link, `created_by null`). Mirror it in `PlatformRestaurantsManager` (hide „Nowy link” for admin owners) so the owner row does not show a dead button.
- Confidence: high.
- `needs-user-decision: yes` (decision 7 kept „Nowy link” unchanged; this narrows it for one account class).

## [low] The scheduler role's trust policy has `aws:SourceAccount` but no `aws:SourceArn` — any schedule in the account may assume it

- Location: `scripts/lib/aws-deploy.mjs:329-342` (`schedulerTrustPolicy`), applied by `createSchedulerRole` and on every deploy by `updateSchedulerTrust` (`:410`).
- Failure scenario: a principal in the same account who can create an EventBridge schedule and pass this role (`iam:PassRole` on `kolacja-podwyzkowa-scheduler`) can invoke the function with any payload through their own schedule. The inline policy limits the role to `lambda:InvokeFunction` on this one function and the app still demands the token, so the worst case is extra invocations (cost) and `POST /api/jobs/retention` 404s — but the prompt asks for confused-deputy conditions and AWS's own guidance for Scheduler is `aws:SourceAccount` AND `aws:SourceArn`.
- Evidence: `Condition: { StringEquals: { "aws:SourceAccount": account } }` and nothing else.
- Fix sketch: add `ArnLike: { "aws:SourceArn": \`arn:aws:scheduler:${region}:${account}:schedule/default/${SCHEDULE_NAME}\` }` (the deploy knows region and account; `updateSchedulerTrust` already rewrites the trust on every run, so existing roles pick it up). Update `tests/scripts/aws-deploy.test.ts` accordingly.
- Confidence: high.
