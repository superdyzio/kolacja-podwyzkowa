## Findings

### [medium] `quiz_question_bump_run` has no self-skip during an event delete → „Usuń trwale” fails with an FK violation whenever the event still has a quiz run
- Location: `supabase/migrations/20261111070000_review_fixes.sql:222-241` (trigger function and `create trigger quiz_question_bump_run after insert or delete on public.quiz_question`), vs the guard the SAME author added one migration later for the identical situation: `supabase/migrations/20261111080000_guest_erasure.sql:64-69` („The event itself is being deleted … a snapshot row updated twice in this transaction would re-check its foreign key against the deleted event"). Caller: `src/lib/events/service.ts:215-229` (`deleteEvent`: a plain `delete from event`, any error → `fail("usunąć wydarzenia")` → 500).
- Failure scenario: an event whose quiz was never „ended" — a `quiz_run` row exists (the demo leaves its main event in phase `results` with 3 questions; a client who shows the results and walks away leaves the same) — and the owner clicks „Usuń trwale" (`DELETE /api/panel/events/<id>`). `delete from event` cascades; the RI cascade triggers on `event` fire in trigger-name order (`RI_ConstraintTrigger_a_<oid>`, i.e. constraint creation order), so `quiz_question`'s cascade (created first in `20261111060000`) runs while the `quiz_run` row still exists. Every deleted question fires the bump trigger: `update public.quiz_run set revision = nextval(...) where event_id = …`. The FIRST update passes (old tuple from an older transaction, key columns unchanged → Postgres skips the FK re-check). The SECOND update's old tuple was written by THIS transaction, and `RI_FKey_fk_upd_check_required` then forces the FK check regardless of unchanged keys → `select 1 from event where id = … for key share` finds nothing (the event row is already deleted in this transaction) → `ERROR 23503: update on table "quiz_run" violates foreign key constraint "quiz_run_event_id_fkey"` → the whole delete rolls back → 500. With a question on the TV (phase `question` / `reveal`) ONE question suffices: `quiz_run_question_fkey … on delete set null` is an `RI_…` trigger too, sorts before `quiz_question_bump_run` and already writes the first new tuple version. Only `quiz_run_action('end')` or a reset of the part `quiz` (both the client's or the dispatcher's business) make the delete possible again — nothing tells the owner why. The retention purge is NOT affected (it deletes no questions); `releaseTestEvent` is affected whenever a test leaves a run.
- Evidence: `review_fixes.sql:224-231` — the trigger body is only the `update public.quiz_run … where event_id = case when tg_op = 'DELETE' then old.event_id else new.event_id end` with no existence check; `guest_erasure.sql:64-69` — the guard for the same mechanism on `seating_snapshot`, explained by the author in words that describe exactly this failure. Untested: `tests/integration/pub-quiz.test.ts:296-307` ends with `runQuizAction(…, { action: "end" })` before `afterAll → releaseTestEvent`; smoke 43 runs „Reset prób” `quiz` (deletes the run) before „the event deleted"; `scripts/demo.mjs` never deletes.
- Fix sketch: in `quiz_question_bump_run`, before the update: `if not exists (select 1 from public.event where id = coalesce(old.event_id, new.event_id)) then return null; end if;` (a new migration with `create or replace`, same signature, trigger unchanged). Add a test that deletes an event in phase `results` with ≥ 2 questions and one in phase `question`.
- Confidence: high (mechanism confirmed by the author's own guard on the sibling trigger; the cascade order is the normal one for constraints created in one migration).

### [low] Lock-order inversion between `guest_erase_published` and `reset_event` / `purge_event_guest_data` → a deadlock window when a guest is deleted while the venue resets
- Location: `supabase/migrations/20261111080000_guest_erasure.sql:71-80` (trigger: guest row already X-locked by the DELETE → `delete from seating_snapshot_seat where guest_id = old.id` → `… seating_snapshot … for update`), vs `supabase/migrations/20261111100000_rsvp_reset.sql:131-135` (`reset_event`: `delete from seating_snapshot` — X on snapshot rows, its cascade X on seat rows — then, several statements later, `:169 delete from public.guest where event_id`), the same order in `purge_event_guest_data` (`review_fixes.sql:170-184`).
- Failure scenario: the venue runs „Reset danych" with `seating` / `guests` / `venue` while the client deletes one seated guest (`DELETE /api/o/<key>/guests/<id>`, or the dispatcher). Reset: holds the snapshot and seat rows, reaches `delete from guest` → waits for the guest row held by the guest delete. Guest delete: holds the guest row, its trigger waits for the seat rows held by the reset → cycle → after `deadlock_timeout` Postgres aborts one of them (40P01 → a 500 for that caller; no data corruption, a retry works). The window is the reset's few milliseconds between its snapshot delete and its guest delete. The purge is practically unreachable this way (every guard purges before the route runs). `publish_seating` vs the trigger is a one-way wait, not a cycle.
- Evidence: the trigger comment claims only „rows locked in id order, so two deletes never deadlock on them" — true between two guest deletes, not against the reset's parent-first order.
- Fix sketch: either accept it (document; the UI already shows the failed request) or make the single guest delete a DB function that takes `pg_advisory_xact_lock(3003, p_event_id)` BEFORE locking the guest row (taking the advisory lock inside the trigger would not help: the guest row is already locked when a BEFORE trigger runs, so the reset — which holds 3003 — would still wait on it).
- Confidence: medium (the cycle is real; the window is tiny).

### [low] The platform administrator's invitation links from „Nowa restauracja" / „Dodaj właściciela" are still not logged for the owner — only „Nowy link" is (the review's fix #3 covers one of two paths)
- Location: `src/lib/platform/service.ts:68-88` (`ownerResult` → `issueStaffToken(db, row.owner_account_id, "invite", createdBy)`, a plain token insert, no `support_log` row), called by `createRestaurantWithOwner` (`:98-121`) and `addRestaurantOwner` (`:126-148`); compare `issue_owner_link` in `review_fixes.sql:54-104` which writes the `link` row in the same transaction.
- Failure scenario: the admin posts `POST /api/panel/platform/restaurants/<id>/owners { email }` for an EXISTING restaurant with an e-mail whose account has no password yet (or a new e-mail). `add_restaurant_owner` makes it an owner, `ownerResult` issues an invitation; opening it logs the admin in AS an owner of a restaurant that already holds guest data — with no `link` entry in the owner's „Dziennik wejść administratora". The PRD's principle the fix was made for (FR-021 / NFR-012: every way of the administrator into a restaurant's data is recorded) holds for „Nowy link" only. (The new owner does appear in the team list, so the existing owner can notice it that way.)
- Evidence: `platform/service.ts:78` `issueStaffToken(...)` with `createdBy` only; no `.from("support_log")` / `issue_owner_link` call on that path.
- Fix sketch: route the invitation of `ownerResult` through `issue_owner_link` (the account is an owner there by then) or a sibling DB function that logs `link` for an invite; or decide explicitly that an invitation at creation is out of scope (then say so next to decision 7 in `m2-review.md`).
- Confidence: high that it is unlogged; whether it must be is the user's call.
- needs-user-decision: yes

**`20261111080000_guest_erasure.sql`**
- Self-skip: the `not exists (select 1 from event where id = old.event_id)` check is sound — a guest row's event can only be invisible inside the event's own delete (the FK `guest.event_id → event` forbids an orphan; a cascade DELETE runs after the event row is gone in the same transaction, and the trigger's query sees that), so it never skips a real guest delete. The test's event B (two seated guests, one snapshot) exercises exactly the double-update path and passes only because of the skip.
- The trigger's own order: seat rows by `guest_id` (index), then snapshot rows `order by id for update`, then `+1` per snapshot — a guest has at most one seat per snapshot (`seat_assignment.guest_id` is its PK; publish copies it), so `+1` equals the backfill's `count(*)` per snapshot. Two concurrent guest deletes of one event lock snapshot rows in the same order.
- `tv_spotlight.guest_id`: composite FK `(event_id, guest_id) → guest (event_id, id)` (the unique key exists, `20261109120000:102`), `on delete cascade`, CHECK `guest_id is null or kind = 'person'`; `drawPersonOnTv` selects `id, display_name`, resolves the picked name to exactly one guest (names unique per event) and inserts `guest_id`; questions/topics insert null. The name match for old-code rows is case-insensitive and limited to `kind = 'person'` of the same event (tested).
- Backfill on production-shaped data: seat rows with `guest_id is null` exist ONLY for guests deleted after a publish (publish always writes a guest id; the purge and the resets delete snapshots before guests), so it deletes exactly the names decision 1 asked to delete and bumps their snapshots; person rows get their guest by name, the rest are deleted. Re-running it changes nothing (idempotent). Deliberately not data-preserving — documented in the migration header and in `m2-review.md` („najpierw eksport").
- `purge_event_guest_data` and `reset_event` delete snapshots and the spotlight BEFORE guests, so the trigger finds nothing there (the guest-erasure test's last case proves the reset).
- `erased_seats` in the tokens, same reads on both paths: TV — `getTvScreenVersion → getSeatingVersion` and `getTvScreen → getTvSeating → toTvSeating` both take `erased_seats` from the ONE `latestSnapshotRow` read (`SNAPSHOT_COLUMNS`), `seatingVersion(id, plan, erased)` → `"<id>-<erased>.<plan>"` only above 0 (other events' tokens unchanged); guest — `getGuestStateVersion` and `getGuestState → toGuestState` both pass `published.erasedSeats` from `getPublishedVersion` into the HASHED part (`erasedPart` only above 0), the two-part prefix and the ≤ 64-character budget untouched; the guest's own seat, the tablemates (`others` rows of the table) and the drawing (`seats` of the snapshot) are all read from `seating_snapshot_seat`, so an erased row is simply absent (`toTablemates` comment updated); tablet — `RestaurantViewDto.seating = toTvSeating(latest snapshot)` sits inside the fingerprint (its `version` and its seat list both change); staff offline copies — `StaffReadoutDto.seating` is the live `TvSeatingDto`, re-saved on every successful read, and `isSeating` only checks `isString(version)` (no pattern on the token, so the new `"<id>-<n>"` shape validates); the organizer's offline readout (`getPublishedSeating`), the export, the restore, the history and `snapshotFingerprint` all read seat rows → an erased seat is empty everywhere, and `upToDate` stays true because the working arrangement lost the guest's seat by cascade (tested). No code splits the seating token on `-` (`partsOf43` splits on `.`); islands compare for equality only.
- Deploy: additive except the deliberate backfill; old code on the migrated DB keeps working (it ignores `erased_seats`, inserts person rows without `guest_id`, which the name match covers); new code on an un-migrated DB fails at `SNAPSHOT_COLUMNS` — migration before code, as stated.
