## Findings

### [low] Smoke section 40: the move's price assertions cannot fail (tautology)
- Location: `scripts/smoke.mjs:10169-10172` — the check "rsvp: „Przenieś wybory do zamówień” — …": `aniaLine40?.unitPriceGrosze === menuPrice40(moved40.data?.board, "Schabowy")` (10170) and `celinaLine40?.unitPriceGrosze === menuPrice40(moved40.data?.board, "Pierogi")` (10172).
- Failure scenario: the check is meant to prove the move priced the lines like `POST /orders` (newest event line, else the catalog). But `OrderBoardDto.menu.items[].priceGrosze` is computed by `orderMenu(available, (name) => eventPriceOf(items, name))` (`src/lib/orders/service.ts:135`, `src/lib/menu/rules.ts:123-133`): the newest event line's price of that name, else the catalog price. After the move, the newest "Schabowy" line IS Ania's and the newest "Pierogi" line IS Celina's, so `menuPrice40(moved40.data.board, …)` equals the moved line's price whatever price the move wrote (0, 999, anything). The price part of the check is a `x === x` comparison.
- Evidence: `priceGrosze: eventPriceOf(item.name) ?? item.priceGrosze` (menu/rules.ts:130); the smoke compares against `moved40.data?.board`, i.e. the board AFTER the insert.
- Fix sketch: compare with the board BEFORE the move, which has zero lines (`ordersBefore40.data?.items?.length === 0` is already asserted), i.e. `aniaLine40?.unitPriceGrosze === menuPrice40(ordersBefore40.data, "Schabowy")` (then `menu.items[].priceGrosze` is the catalog price), or against the catalog price A's manager set in section 32.
- Confidence: high

### [low] Move-to-orders: idempotency keyed by the dish's CURRENT catalog name only — a catalog rename between two moves duplicates lines
- Location: `src/lib/rsvp/orders.ts:46-57` (`have` set and the skip test), `src/lib/rsvp/orders-service.ts:23` (the line read selects `id, name, guest_id, unit_price_grosze` — no `menu_item_id`), `src/lib/rsvp/service.ts:92` (`readRsvpGuestSources` selects `menu_item(name, course)` — no `menu_item_id`).
- Failure scenario: the client moves the choices (Ania → one line "Schabowy", `menu_item_id` = the item). The venue renames the catalog item to "Kotlet schabowy" (menu-catalog-courses allows it; ordered lines keep their spelling by design). More guests answer; the client clicks "Przenieś wybory do zamówień" again. Ania's RSVP dish now reads "Kotlet schabowy" (`guest_rsvp.menu_item(name)` is the live join), `dishKey("Kotlet schabowy") !== dishKey("Schabowy")`, so Ania is not in `have`, the preview says "added N+1" and the POST inserts a SECOND line for her — the feature's own promise ("Kto ma już to danie w zamówieniu, zostaje pominięty… można przenieść ponownie", `rsvpMessages.moveIntro`) breaks, and the bill double-counts the dish.
- Evidence: `const have = new Set(lines.flatMap((line) => (line.guestId === null ? [] : [\`${line.guestId}|${dishKey(line.name)}\`])));` … `if (have.has(\`${guest.id}|${dishKey(guest.dish)}\`)) { skipped += 1; continue; }`.
- Fix sketch: select `menu_item_id` in `readRsvpGuestSources` (service.ts:92) and carry it on `RsvpGuestSource.answer`; select `menu_item_id` in `planFor`'s line read (orders-service.ts:23); in `planRsvpOrders` treat a line with the same `guestId` and a non-null `menuItemId` equal to the answer's as "has it" too. Name matching stays as the fallback for free-text lines.
- Confidence: high

### [low] Guest-facing privacy texts promise a daily automatic clean-up unconditionally, while the schedule is optional at deploy time
- Location: `src/lib/privacy/messages.ts` — `retentionIntro` (PL line 13, EN line 45) and `privacyNoticeMessages.retentionText` (PL line 196, EN line 239); the condition in `scripts/lib/aws-deploy.mjs` (`RETENTION_TOKEN` in `OPTIONAL_KEYS`, `retentionPlan` "POMINIĘTE") and `scripts/deploy-aws.mjs` (`if (environment.RETENTION_TOKEN) { … } else { … retention = "missing-token" }`); README "`RETENTION_TOKEN=… (zalecane)`".
- Failure scenario: the user deploys without `RETENTION_TOKEN` (allowed, printed as a hint only). Every restaurant page says "Potem usuwa je automatycznie codzienne sprzątanie danych" and every guest's privacy notice `/g/<key>/prywatnosc` (a legal draft, GDPR information duty) says "After that a daily automatic clean-up deletes it — at the latest, it goes the next time the event is opened". No daily clean-up exists on that deployment; a dormant venue's guest data stays in the database indefinitely (exactly the gap the user's decision 3 was meant to close), while the notice asserts otherwise. The second half of the sentence ("at the latest … opened") is true, the first half is a promise the deployment may not keep.
- Evidence: `retentionIntro: "… Potem usuwa je automatycznie codzienne sprzątanie danych, a najpóźniej dzieje się to przy następnym otwarciu wydarzenia. …"`; `OPTIONAL_KEYS = ["AI_PROVIDER", "ANTHROPIC_API_KEY", "AI_MODEL", "RETENTION_TOKEN"]`.
- Fix sketch: either make `RETENTION_TOKEN` REQUIRED in `validateDeployEnv` (a deploy without the schedule then fails early, matching the texts), or soften both texts to what every deployment guarantees ("są usuwane po terminie — najpóźniej przy następnym otwarciu wydarzenia").
- Confidence: high
- needs-user-decision: yes

### [low] CI never runs the retention job's positive path: smoke section 46's token branch is permanently SKIP there
- Location: `.github/workflows/ci.yml:48-52` (`npm run preview -- --port 4321 &` … `BASE_URL=http://localhost:4321 npm run smoke`, no `RETENTION_TOKEN`); `scripts/smoke.mjs` section 46 (`if (!jobToken46) { console.log("SKIP …") } else { … }`).

A regression in the route's happy path (e.g. the body parser, `runGuestRetentionJob` wiring, the `no-store` header on 200) would pass CI; the m2-review's "893 PASS with a test token" was a one-off local run.

- Fix sketch: in the `smoke` job export one fixture token to both commands, e.g. `RETENTION_TOKEN=0123456789abcdef0123456789abcdef npm run preview -- --port 4321 &` and the same env on `npm run smoke` (the token is a CI fixture, not a secret).
- Confidence: high

### [low] Kitchen tablet: the readout link is decided by the server clock at render, so a tablet opened before midnight and left open saves from midnight but shows no link until a reload

Cosmetic; nothing is lost.
- Fix sketch: render the link from the island (it knows `saved`), or show it whenever `saved` is set.
- Confidence: high (behaviour), low impact
