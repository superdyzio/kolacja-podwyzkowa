# Review 2 — privacy and data exposure (PR #4 at 163803b)

Angle: NFR-019 (retention), NFR-021 (no guest data to AI), GDPR art. 9 (diets/allergies), key and secret exposure, logs, HTML, browser storage, white-label.

Method: read every anchor path end to end (guard → service → DB function), compared the purge against every table/column of `src/db/database.types.ts` that can hold a guest's name, note or diet, and checked the guest notice / policy drafts against the code. No tests, no DB, no git writes.

Overall: the hard invariants hold (see "Checked and fine"). The real defects of this angle are in what the guest is *promised* versus what the code does, and in one erasure gap.

---

## Findings

### [medium] Deleting a guest does not erase them: the name stays in every published snapshot and on the TV until the retention purge
- Location: `src/lib/guests/service.ts:229-235` (`deleteGuest` = one plain `delete`), `supabase/migrations/20261027014210_create_seating.sql:118-119` (`seating_snapshot_seat.guest_id … on delete set null`, `guest_name text not null` — the name is kept; the multi-tenant migration `20261109120000` rewrote only the insert, not this FK), `src/lib/seating/published.ts:149,182` (`name: seat.guestName` for the TV and the prints), `src/lib/guest-links/service.ts:110-131` (tablemates read `guest_name`, no guest filter), `src/lib/tv-spotlight/service.ts:105-122` (`drawPersonOnTv` stores the name as text), `src/lib/privacy/messages.ts:185` (`rightsText` promises deletion "przed tym terminem" via the venue).
- Failure scenario: a guest asks the venue to be removed (art. 17), or the client simply deletes a mistaken entry after the first publish. The guest row (and with it diets, RSVP, guess, key) goes, but `seating_snapshot_seat.guest_name` survives in EVERY snapshot of the event (the migration comment at `20261111050000_privacy_retention.sql` even calls it "the only copy of names that survives a guest delete"). Until somebody republishes, the TV (`toTvSeating`), the staff tablet, the prints (`toPublishedSeating`) and every tablemate's phone (`guestSeat` → `others`, `GuestDrawingDto.tables[].seats`) keep showing the name; after a republish, the historical snapshots still hold it until `purge_event_guest_data` runs (up to 365 days). A name put on the TV by „Wylosuj osobę na TV" stays in `tv_spotlight.text` until hidden or replaced. The only erasure tools before the term are the venue's full reset part `seating` (deletes all snapshots) or waiting for the purge — neither is what the guest notice describes. `src/lib/guest-links/state.ts:144` documents the behaviour ("a deleted guest's row has no id but still shows") as intended for v1, but M-2 now promises erasure.
- Evidence: `deleteGuest` → `db.from("guest").delete().eq("id", id).eq("event_id", eventId)`; no trigger, no snapshot update anywhere (`grep guest_name src/lib` finds only reads); `drawPersonOnTv` → `show(db, eventId, "person", name)`.
- Fix sketch: in a `before delete on guest` trigger (or in `deleteGuest`), `update seating_snapshot_seat set guest_name = '' where guest_id = old.id` (the column is `not null`, an empty string is allowed; or make it nullable) and `delete from tv_spotlight where event_id = old.event_id and kind = 'person' and text = old.display_name`; the TV then shows an empty chair and `isUpToDate` correctly turns to "unpublished changes". Document that snapshots are immutable except for erasure.
- Confidence: high (behaviour), medium (severity depends on how the user reads art. 17 for M-2).
- needs-user-decision: yes

### [low] The guest privacy notice no longer describes what the TV and the quiz do
- Location: `src/lib/privacy/messages.ts:165-175` (`dataItems`), `:176-178` (`audienceText`), EN `:207-220`; versus `supabase/migrations/20261111060000_pub_quiz.sql:427-428` (`quiz_tv_state` → `'top'` with `g.display_name` and points), `src/lib/tv-spotlight/service.ts:105-122` (a drawn guest's name on the TV), `guest.group_id` / `getGuestList` in `src/lib/guests/service.ts` (group membership).
- Failure scenario: a guest reads `/g/<key>/prywatnosc`: "Inni goście i ekran na sali widzą tylko imiona przy stolikach z opublikowanego rozsadzenia". While the pub quiz is at "results" the TV shows the names and points of places 1–3 (PRD-sanctioned, FR-049 + the non-goals' exception, so the behaviour is fine — the notice is wrong), and „Wylosuj osobę na TV" shows a guest's name over the plan. The data list omits the quiz answers / points / place (which the policy draft `src/lib/legal/privacy-policy.ts:104` does list) and the group membership — the notice was written in S-26 and not updated by S-28, although CLAUDE.md's own rule for the drafts says to update them with every change of "what data is kept, who sees it".
- Evidence: `audienceText: "Organizator wydarzenia i obsługa lokalu. Inni goście i ekran na sali widzą tylko imiona przy stolikach…"`; `dataItems` = name/absence, RSVP, diets, seat+orders, guess — no quiz, no group.
- Fix sketch: add the quiz (answers, points, place; names and points of places 1–3 on the TV at the results) and the TV person draw to `dataItems`/`audienceText` in PL and EN; mention groups.
- Confidence: high

### [low] Support mode prints the full staff list (every guest's diets and notes) although the export is refused for exactly that reason
- Location: `src/pages/panel/wydarzenia/[id]/wydruki/[kind].astro:19-22` (`findPanelEvent` — support branch included — then `getRoomPrintSource(…, { diets: kind === "lista-obslugi" })`), versus `src/lib/panel-api.ts:190-193` and `src/pages/api/panel/events/[id]/export.ts:18-20` ("a bulk copy of guests' health data is never part of support"). The dispatcher's `klient/guests` GET (`GuestListDto` with `diets`, `dietNote`) is open to support too (`src/lib/client-routes/match.ts:63` blocks only the key routes).
- Failure scenario: the platform admin in a logged support visit opens `/panel/wydarzenia/<id>/wydruki/lista-obslugi` and gets a print-ready A4 list of all present guests' diets, allergies and notes — the same bulk health data the export deliberately refuses to support mode. Behaviour is consistent with the PRD's "pełny wgląd w dane każdej restauracji" and CLAUDE.md documents it, so this is an internal policy contradiction, not a guard bug; the policy draft (`privacy-policy.ts:108`) tells guests the admin sees diets during a logged visit, so the public statement matches the print, not the export.
- Fix sketch: decide one rule: either refuse `lista-obslugi` (and the `goscie` preview's diets) to `panel.support` like the export, or drop the "never part of support" rationale from the export and keep the log row as the control.
- Confidence: high (behaviour); the defect is the contradiction.
- needs-user-decision: yes

### [low] NFR-019 deletion is lazy; the guest notice and the policy state it as unconditional
- Location: `src/lib/privacy/service.ts:18-23` (callers of the purge: guards, panel-page sweep, CLI), `src/middleware.ts:111-116` (sweep only on `GET /panel/**` with a session), `src/lib/privacy/messages.ts:182-184` (`retentionText`: "są usuwane automatycznie … — po {date}"), `src/lib/legal/privacy-policy.ts:109` ("Po terminie usuwamy gości…").
- Failure scenario: a tenant's events whose links are never opened again, on a platform where no staff member of any restaurant opens a panel page (or the operator never runs `npm run retention`), keep their guests' names, diets and notes in the database past the promised date — indefinitely. Every *read path* is clean (the guards purge first), so nothing is ever served, but the data remains in Postgres (and its backups). This is the logged decision "no scheduler — the user's later infrastructure decision" (overnight-log, CLAUDE.md), so not a code defect; it is surfaced because the guest-facing texts promise a date and NFR-019 says the data "znikają z platformy".
- Fix sketch: schedule `npm run retention` (or `pg_cron` on Supabase) before go-live, or soften the notice to "najpóźniej przy następnym użyciu systemu po {date}".
- Confidence: high
- needs-user-decision: yes

### [low] Table-middle order-line notes reach every tablemate's phone
- Location: `supabase/migrations/20261107120000_order_piece_delivery.sql:86-120` (`guest_order_lines` returns `'note', item.note` for own lines AND for every line with `table_id = guest_published_table_id(p_guest_id)`), `src/lib/orders/pieces.ts:96-106` (passes `note` through), `src/components/guest/GuestOrderView.tsx:141` (renders it).
- Failure scenario: the client adds a line for the middle of table 3 with the note „bez orzechów — Ania ma alergię" (the natural place to put it — the kitchen reads notes). Every guest seated at table 3 sees that note on their phone. Diets themselves never reach a guest (checked, `privacy.test.ts`), but a free-text note is an unguarded channel for the same health data, and the PRD gives a guest "tylko własne dane: miejsce, strzał, „Dotarło"…" — a shared line's note is arguably not "own data".
- Fix sketch: drop `note` for `kind: "table"` lines in `guest_order_lines` (or in `toGuestOrderLines`), keep it for own lines; the note stays on the tablet and the floor.
- Confidence: medium (design decision of guest-delivered; the leak needs a client to write health data into a shared note).
- needs-user-decision: yes

## Checked and fine

- **Purge completeness** (`20261111050000_privacy_retention.sql` vs every table in `database.types.ts`): guests deleted (cascades take `guess`, `seat_assignment`, `guest_rsvp`, `quiz_answer`, `quiz_score`, the link key; set-null on `ai_topic`, `order_item`, `order_piece`); `guest_group`, ALL `seating_snapshot` (+ `_table`, `_seat`, `_room` by cascade), `tv_spotlight`, `event_waiter` deleted; `order_item.note` nulled; `guest_access_enabled` off. `quiz_run`, `ai_topic`, `drink_item`, `menu_item`, `event_rsvp_option`, `event.brand_name`, logos and `support_log` hold no guest names (the log's `event_name`/`reason` snapshots are the owner's audit log, append-only by PRD; `reason` is free text typed by the admin — keep that in mind for the DPA). Templates excluded in `purge_event_guest_data` and `expired_guest_data_events`. The TS rule `isGuestDataExpired` (`platformToday(now) > event_date + N`) equals the SQL `guest_data_expired`.
- **Purge triggers**: all four key branches of `resolveAccess` and `findEventMembership` call `enforceGuestRetention` before returning; the guest branch denies on any purge result; `findPanelEvent`'s support branch purges after logging; the floor guards (`findFloorEvent`, `findWaiterFloorEvent`) need none because the floor window (noon next day) always ends before the earliest purge (00:00 two days after); the sweep is global (all restaurants) and throttled; the CLI refuses a remote DB without `--remote`.
- **Guest DTO** (`GuestStateDto`): own name, seat, own guess/place, own RSVP (names and courses only), own quiz answer/points/place (correct option only after close), own + table order lines (`markerFor` collapses other guests' ids to `"guest"`), the published drawing with names (the PRD's explicit allowance); `guest_rsvp_state` and `quiz_guest_state` are filtered by the guest; `OrganizerAccess.event.restaurantKey` is rendered nowhere (`grep restaurantKey src/pages src/components` → none).
- **TV DTO**: names at chairs, spotlight text, quiz counts; names only at the results step for places ≤ 3 — sanctioned by FR-049 and the non-goals' explicit exception. `?sala=` is resolved against the snapshot's rooms and never echoed.
- **Tablet DTO** (`toRestaurantView`): no prices, ids, keys or absences; diets at published seats + unplaced present guests (PRD gives the kitchen diets). The staff offline copy (`staffReadoutFromView`/`FromBoard`) carries the same projection, one fixed key per area, hard expiry at the floor window (earlier for a per-event waiter), swept on live/readout/login pages, cleared on the app's denial; logged decision S-27. The service worker caches only `<scope>/odczyt` (data-free) and `/_astro/`, never the staff-list print or any API answer.
- **Prints**: `diets: true` only for `lista-obslugi` on all four pages; client print HTML carries no key (relative `kind?…`, `../wydruki`, `./logo`); no prices, ids, QR; `@page { margin: 0 }`; `languageSwitch={false}`.
- **Export**: members only (`panelMemberEventApi`, no support branch), guests/tables/rooms by name, no ids/keys/hashes (read `getEventExport` end to end); CSV formula guard seen in `export.ts:10-11,48-49` (the BOM per CLAUDE.md, not read); attachment + nosniff; the event id in the filename is already in the URL.
- **White-label**: `PRODUCT_NAME` appears only on `/`, `/logowanie`, `/haslo`, `/panel*`, the legal pages and staff message dictionaries; every guest/TV/tablet/print/waiter page passes its own title; `NoAccess`, `500.astro` and the config banner name no product. The 500 page echoes no error text.
- **Headers / Referer**: keyed areas get `no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag`; staff and waiter areas `no-store`, `same-origin`, `X-Frame-Options: DENY`; a grep of `https?://` over the guest/TV/tablet/client/print surfaces and the panel/legal/door surfaces finds one external link, the panel's console link (`AiCosts.astro:29`, under the `same-origin` policy); `TvRoomLinks` uses `rel="noreferrer"`; no keyed page links out.
- **AI**: `topicSystemPrompt`/`buildTopicPrompt` take category, theme and locale only; `buildLayoutPrompt` takes room/table names, shapes, seats, positions and the plan image; `venue-ai/service.ts` imports no guest module (read). That `privacy.test.ts` guards the imports and `tests/setup/no-ai-network.ts` blocks the real API: per CLAUDE.md, not read.
- **Logs**: the five `console.error` calls (`event.ts`, `privacy/service.ts`, `reset/service.ts`, `templates/service.ts`, `drinks-service.ts`) log DB error objects/messages only — no bodies, names, diets or keys; the CLI prints links by design.
- **Browser storage**: the guest page stores only draw memory and the last AI topic (as the notice says); the client's S-09 copy (names + guess board, no expiry) is overwritten by the next successful read after a purge — `useOfflineSync.ts:69` calls `saveOfflineSeating(apiBase, result.published, …)` which accepts `null` — accepted for the client's own device.
- **Support strip**: `GET /api/panel/events/<id>` returns `supportEventSummary` (no links/rooms — read); the dispatcher refuses `guest-links*`, `reset`, `restaurant-link`, `trial-reset` (`match.ts:60-66`); that the event PAGE in support mode renders no link rows or waiter credentials: per CLAUDE.md, not read.
