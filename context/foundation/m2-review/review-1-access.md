## [high] Module gate (`module-off` / paid-module lock) bypassed by percent-encoding one letter of the sub-path

- Location: `src/middleware.ts:159-166` (`offModuleOf` → `keyedApiSubPath(pathname)`), `:215-225`; `src/lib/modules/rules.ts:89-131` (`moduleForApiPath`, `keyedApiSubPath`). Root cause shared with the low finding below: the middleware classifies `context.url.pathname` RAW, while Astro matches routes on the DECODED pathname (`node_modules/astro/dist/core/routing/match-request.js:35` `pathname = safeDecodePathname(manifest, pathname)`; `core/app/base.js:157-176`).
- Failure scenario: a new event (DB defaults: `aiTopics` off AND locked, PRD FR-031 / NFR-023) with guest links on. Anyone holding a guest key `G` (or the client holding `K`) sends `POST /api/g/<G>/%61i-topics {"category":null}` (`%61` = `a`). Middleware: `parseAccessPath` grants the key (its regex only needs `(o|tv|g|r)/<key>`), `keyedApiSubPath` yields `"%61i-topics"`, `moduleForApiPath("guest","%61i-topics")` → `null` → no 404. Astro decodes the path and runs `src/pages/api/g/[key]/ai-topics.ts`, whose `guestApi(locals)` passes (access is set) → `generateTopic` → a real Anthropic call and a 200 topic for a module the venue never offered / the client never paid for. Same for the organizer `POST /api/o/<K>/%61i-topics`, `/%67uesses` (PATCH intake), `/%71uiz/run`, `/%71uiz/questions`, `/%73eating/draft`, `/tv-%73potlight`, and the guest `PUT /api/g/<G>/%67uess`, `/%71uiz`, `POST /%71uestions/draw`. CLAUDE.md states gates live "at the EDGE only, never in services": none of these routes re-checks `access.event.modules` (verified: 0 hits in all twelve route files; `ai-topics/service.ts`, `quiz/service.ts`, `guesses/service.ts` never read modules). The panel dispatcher is NOT affected (it uses Astro-decoded `params.path`); the lead rule survives (`isOrganizerApiPath` looks at the `/api/o/` prefix only).
- Evidence:
  - `src/middleware.ts:160` `const keyed = keyedApiSubPath(pathname);` with `pathname` from `context.url` (line 174), never decoded.
  - `src/lib/modules/rules.ts:126` `const match = /^\/api\/(o|g)\/[^/]+\/(.*)$/.exec(pathname);` → `subPath` = raw `%61i-topics`; `:90-91` `const first = subPath.split("/")…; switch (head)` → `default: return null`.
  - Astro: `match-request.js:33-35` `pathname = prependForwardSlash(stripRequestBase(url.pathname, manifest.base)); pathname = safeDecodePathname(manifest, pathname);` → `/api/g/<G>/ai-topics` matches `ai-topics.ts`.
  - `src/pages/api/g/[key]/ai-topics.ts:18` guards only with `guestApi(locals)` (organizer: `src/pages/api/o/[key]/ai-topics.ts:32`), then `generateTopic(…)`.
- Bound: the spend stays capped by `reserve_ai_topic` (`MAX_GUEST_TOPICS` 25 per guest, `MAX_EVENT_TOPICS` 1000 per event, `src/lib/ai-topics/limits.ts:10-12`), which runs inside `generateTopic` regardless of modules — so the exposure is a bypass of the venue's offer and of the paid-unlock rule (and of every other module switch), not unbounded cost.
- Fix sketch: decode once at the top of `onRequest` (mirror Astro: `try { decodeURI(pathname) } catch { deny }`) and feed the decoded path to `classifyAuthPath`, `classifyWaiterPath`, `parseAccessPath`, `keyedApiSubPath`, `isOrganizerApiPath`; additionally refuse (404) any request under `/api/{o,tv,g,r}/`, `/api/panel/`, `/api/kelner/` whose raw and decoded pathnames differ. Add a smoke check (`%61i-topics` on an event with AI topics off → 404 for the guest, 409 `module-off` for the client).
- Confidence: high

## [medium] Open redirect through the `?lang=` language switch

- Location: `src/middleware.ts:174-188`.
- Failure scenario: an unauthenticated victim opens `https://<app>//evil.com/?lang=pl` (or `https://<app>/\evil.com/?lang=pl`, since the URL parser folds `\` to `/`). The node adapter builds the request URL by string concatenation (`node_modules/astro/dist/core/app/node.js:236-239` `new URL(`${protocol}://${hostnamePort}${path}`)`), so `context.url.pathname === "//evil.com/"` (verified with Node: `new URL("https://app//evil.com/x?lang=pl").pathname === "//evil.com/x"`, host stays `app`). No route matches, Astro renders the 404 route and still runs the middleware (`core/fetch/fetch-state.js` skipMiddleware default `false`; set `true` only for the re-render after a middleware failure), the `lang` branch fires first and answers `303 Location: //evil.com/` — a scheme-relative URL every browser resolves to `https://evil.com/`. Astro's `redirect()` passes the string through untouched (`core/middleware/index.js:51-57`). Phishing via a trusted domain; the locale cookie is set on the way.
- Evidence: `src/middleware.ts:185-187` `const target = new URL(context.url); target.searchParams.delete(LOCALE_PARAM); return context.redirect(`${target.pathname}${target.search}`, 303);`
- Fix sketch: `const safePath = "/" + target.pathname.replace(/^\/+/, "");` and redirect to `${safePath}${target.search}`; do NOT use `new URL(path, origin).href` (it resolves `//evil.com` to the attacker's host too). Optionally skip the switch when no route matched.
- Confidence: high (code path); medium that the AWS Function URL / Lambda Web Adapter forwards `//` unnormalised — locally (`npm run preview`) it is reproducible as written.

## [medium] Platform admin's „Nowy link” for an owner WITH a password is a reset link: unlogged, unbounded owner-level access

- Location: `src/lib/platform/service.ts:179-203` (`issueOwnerLink`: `kind = password_hash === null ? "invite" : "reset"`), `src/pages/api/panel/platform/restaurants/[id]/owners/[accountId]/link.ts:13-28`; `supabase/migrations/20261109140000_staff_accounts.sql:154-183` (`redeem_staff_token` sets the password, deletes every session of the account, opens a new one for the redeemer).
- Failure scenario: an admin (no support grant, or a grant that expired) calls `POST /api/panel/platform/restaurants/<id>/owners/<ownerAccountId>/link` for an owner who already has a password → gets `/haslo/<token>` (24 h) → opens it, sets a new password → is logged in AS the owner: full write access to the restaurant (events, links incl. the client/TV/tablet keys that support mode deliberately hides, team, settings), no 60-minute box, and NOT ONE `support_log` row (only `begin_support_access` / `record_support_access` / `set_event_module_unlock` write it). PRD v2 line 185 (FR-021) and NFR-012 (line 279): "każde jego wejście w dane lokalu jest zapisane i widoczne dla właściciela lokalu". The owner only notices indirectly (sessions dead, password changed). If the account is an owner of several restaurants, the takeover spans all of them.
- Evidence: `platform/service.ts:197` `const kind = data.staff_account.password_hash === null ? "invite" : "reset";` `:198` `issueStaffToken(db, accountId, kind, createdBy)` — no grant check, no log write; `staff_accounts.sql:174-180` `update public.staff_account set password_hash = …; delete from public.staff_session where account_id = …; insert into public.staff_session …`.
- Fix sketch: write a `support_log` row (new kind `link`, snapshot of the admin and the target e-mail) whenever `issueOwnerLink` issues a `reset` (and arguably an `invite`), so the owner's log shows it; or allow a reset link only inside a live support grant. Keep invites for password-less accounts as they are.
- Confidence: high that the path exists and is unlogged; the severity is a product judgement.
- needs-user-decision: yes — a logged decision (`context/foundation/overnight-log.md:50` S-10 „Nowy link … inaczej link resetu 24 h", `:73` S-12 names the takeover mechanic and defers the admin case, `:93` S-13 leaves it open) that conflicts with the PRD's audit rule.

## [low] Staff and key areas are classified on the raw pathname, so a percent-encoded path skips the middleware layer entirely (no data opens, but the layer's guarantees vanish)

- Location: `src/middleware.ts:174,193-204`; `src/lib/auth/paths.ts:19-34`; `src/lib/event-waiters/paths.ts:33-47`; `src/lib/access/paths.ts:20-30`.
- Failure scenario: `GET /%70anel/restauracje/5` with a valid `kp-session`: `classifyAuthPath` → null → `locals.staff` stays null → Astro (decoded) renders `restauracje/[id].astro` → `findPanelRestaurant` returns null → the NoAccess page WITHOUT `Cache-Control: no-store`, `X-Frame-Options: DENY`, `X-Robots-Tag`; without a session the answer is that 404 page instead of the documented 303 to `/logowanie`, a stale cookie is not cleared, the retention sweep does not run, `staffRequest` is null. `/%6Cogowanie` is frameable (clickjacking of the login form). `POST /api/%61uth/login` / `/api/%6Belner/wejscie` skip OUR Origin pre-check; Astro's own `security.checkOrigin` (default `true`, `core/config/schemas/defaults.js:44`; `core/pages/handler.js:70`) still refuses cross-site form-like posts, so no CSRF was found. Every data route and page re-checks `locals` (`panelApi`, `findPanel*`, `findFloorEvent`, `findWaiterFloorEvent`, `organizerApi`, `guestApi`, `restaurantApi`, `accessFor` — verified for ALL files under `src/pages/{o,tv,g,r}` and `src/pages/api/{o,tv,g,r}`), so this is a defense-in-depth gap, not a leak — except for the module gate above, which has no second check.
- Evidence: `src/middleware.ts:174` `const { pathname } = context.url;` vs `node_modules/astro/dist/core/routing/match-request.js:35`.
- Fix sketch: the same decode-once fix as the high finding; the regexes in `auth/paths.ts`, `event-waiters/paths.ts`, `access/paths.ts` then see what Astro sees.
- Confidence: high

- `/r/` and `/tv/` API folders export GET only (venue links read-only, PRD rule 1); `restaurant-link` and `reset` on the client link answer the identical 404; `restaurantKey` / `tvKey` / `organizerKey` appear in no `src/pages/api`, `src/components` or `src/pages/panel` output except the owner/manager `EventCard`.
