# Review 3 — database migrations and DB functions (PR #4 at 163803b)

Scope: the 17 migrations `20261109120000_multi_tenant_events.sql` … `20261111060000_pub_quiz.sql` (each read fully, compared with the pre-M-2 functions they replace), `src/db/database.types.ts`, and the TS callers of every `.rpc(` (47 call sites) at the SQL↔TS seam.

Overall verdict: the SQL is in good shape. I found no critical/high defect. Every new table has RLS on and `revoke all … from anon, authenticated`; every function sets `search_path = ''` and qualifies names; all 13 replaced v1 signatures are dropped explicitly before recreation; the data-dependent steps preserve event 1 and its keys; advisory-lock ordering is consistent except for one gap (finding 1). The findings below are low severity.

## Findings

### [low] `purge_event_guest_data` does not take the quiz lock `(3013, event)` that `reset_event` takes — deadlock window with `quiz_run_action('results')`
- Location: `supabase/migrations/20261111050000_privacy_retention.sql:130-131,159` (locks 3003, 3008, event row; then `delete from public.guest`), vs `supabase/migrations/20261111060000_pub_quiz.sql:603-606` (reset adds `pg_advisory_xact_lock(3013, p_event_id)`) and `:221-234` (`results`: `delete from quiz_score` + `insert into quiz_score … guest_id`).
- Failure scenario: an event past its retention term still has a quiz; the client clicks „Pokaż wyniki” while the purge runs (the purge is triggered by the first request of an expired event — including the client's own request, so two near-simultaneous requests are needed). `results` holds the `quiz_run` row and X-locks on `quiz_score` rows, then needs KEY SHARE on `guest` rows (FK of the insert); the purge holds X on `guest` rows and its RI cascade needs X on the same `quiz_score` rows → Postgres deadlock, one transaction aborted (a 500 for the client or a retried purge). No data corruption.
- Evidence: the privacy migration's comment says "Locks like reset_event: (3003, event), (3008, event), then the event row" — written before pub-quiz added 3013 to `reset_event` only.
- Fix sketch: add `perform pg_advisory_xact_lock(3013, p_event_id);` after line 131 of the privacy migration (new migration with `create or replace`, same signature).
- Confidence: high that the lock is missing; the scenario itself is unrealistic (a quiz ≥ 2 days after the event).

### [low] CLAUDE.md says support mode ends "with a password change", but `change_staff_password` keeps the calling session and therefore its `support_grant`
- Location: `supabase/migrations/20261109140000_staff_accounts.sql:192-205` (`delete from public.staff_session where account_id = p_account_id and id <> p_keep_session_id`), `supabase/migrations/20261110160000_admin_support_log.sql:31` (`support_grant.session_id … on delete cascade` — the only automatic end), `src/lib/auth/service.ts:314-318` (passes `p_keep_session_id: session.sessionId`; no `end_support_access` anywhere under `src/lib/auth` or the password route).
- Failure scenario: a platform admin in support mode of restaurant R changes their password in the same browser → their session survives by design, and so does the live grant on R (up to its 60-minute box). CLAUDE.md ("Platform admin's support access … It ends … with the login session (logout, „Wyloguj wszędzie”, a password change, a used reset link)") promises otherwise. Security impact is negligible (same person, same session, still read-only and logged) — this is a claim the code does not honour.
- Fix sketch: either add `delete from public.support_grant where session_id = p_keep_session_id;` to `change_staff_password` (no `exit` row would be logged — or call `end_support_access` for each live grant of that session from the TS route), or correct the CLAUDE.md sentence.
- Confidence: high.

### [low] Migrations 2–17 rely on Supabase default privileges for `service_role` EXECUTE / sequence USAGE (no explicit grants, unlike migration 1 and every pre-M-2 migration)
- Location: e.g. `supabase/migrations/20261109140000_staff_accounts.sql:246-250`, `…20261111060000_pub_quiz.sql:45,77,252,298…` — each `revoke execute … from public, anon, authenticated` (and `revoke all on sequence quiz_run_revision_seq from anon, authenticated`) with no `grant execute … to service_role`; `20261109120000_multi_tenant_events.sql:855-867` and all v1 migrations grant explicitly.
- Failure scenario: none on Supabase (local and hosted share the `ALTER DEFAULT PRIVILEGES … TO service_role` setup, and CI's smoke proves the RPCs run as `service_role`). On a vanilla Postgres, or if the default privileges ever change, every new RPC — and every INSERT into `quiz_question`, whose CHECK evaluates `public.quiz_options_valid()` as the inserting role — would fail with `permission denied for function`. Noted because the repo's own convention ("New DB functions: `set search_path = ''` and `revoke execute …`" + the explicit `grant … to service_role` in every earlier migration) is not followed consistently, so a future reader may assume the explicit grant is there.
- Fix sketch: a follow-up migration granting EXECUTE on the new functions and USAGE on `quiz_run_revision_seq` to `service_role` (idempotent); or document the reliance in CLAUDE.md.
- Confidence: medium (fragility, not a current failure).

## Checked and fine

**Apply cleanly on production-shaped data (event 1 + children):**
- Migration 1 (`multi_tenant_events`): `restaurant` row inserted only `where exists (select 1 from event)`; `event.id` `smallint`→`integer` with the singleton CHECK dropped, default dropped, identity added, `setval(max+1, false)`; all 14 child `event_id` columns altered to `integer` and their defaults dropped (every pre-M-2 table with `event_id` is covered); `restaurant_id` backfilled to `min(restaurant.id)` then `set not null`; new CHECKs (`event_name_format`, `restaurant_name_format`) hold for 'Kolacja podwyżkowa' / 'Restauracja domyślna'. Keys (`organizer_key`, `tv_key`, `restaurant_key`) are never touched; the old `event_keys_distinct`/format checks stay. The composite FKs `(event_id, x) → (event_id, id)` with `on delete set null (col)` (PG 15+) are consistent for v1 rows (all `event_id = 1`). Old FK names dropped (`guest_group_id_fkey`, `venue_table_room_id_fkey`, `seat_assignment_*`, `ai_topic_guest_id_fkey`, `order_item_*`, `order_piece_*`) exist on main with those auto-generated names.
- The 13 `drop function` statements match the old signatures exactly (incl. `save_guest_guess_with_place(bigint, integer, integer)`, `set_order_pieces(bigint, integer[], boolean, bigint)`, `reserve_ai_topic(smallint, …)`, `ai_topic_usage(smallint, bigint)`): no stale overload is left callable, no PostgREST ambiguity. `guest_published_table_id` / `guest_order_lines` are correctly left as they were: the old body already scopes the snapshot to the guest's own event.
- Later backfills: `event_date = (created_at at time zone 'Europe/Warsaw')::date` then NOT NULL + default (m4); `menu_mode` added with default `'off'` then default switched to `'full'` (m9); `modules_enabled` = five v1 modules + `modules_unlocked = {aiTopics}` for every existing row (m10; also hits pre-existing templates, documented in the migration); `guest_retention_days` default 30 (m16: nothing deleted by the migration itself — the first read after deploy purges events past their term, as CLAUDE.md warns; the archive DB never gets it). Scale-150 drops/re-adds `venue_table_seat_count`, `seating_snapshot_table_seat_count`, `guess_predicted_place_range` (names verified on main) with wider ranges — data-preserving.

**Security:**
- All 17 new tables (`restaurant`, 5 staff tables, `support_grant`, `support_log`, `menu_item`, `event_menu_item`, `restaurant_logo`, `event_logo`, `event_waiter`, `event_rsvp_option`, `guest_rsvp`, `retention_sweep`, `quiz_question`, `quiz_run`, `quiz_answer`, `quiz_score`) have `enable row level security` + `revoke all … from anon, authenticated`; the one new sequence is revoked too.
- Every new/replaced function: `set search_path = ''`, fully qualified `public.*` / `extensions.gen_random_bytes`, `revoke execute … from public, anon, authenticated` (trigger functions included). `create or replace` of `platform_restaurant_list`, `record_support_access`, `reset_counts`, `reset_event` keeps the existing ACLs. No `security definer` anywhere (good: no escalation surface).
- Tenant isolation at the DB level: `event_menu_item`, `event_rsvp_option`, `guest_rsvp`, `event_waiter` use composite FKs through `event (id, restaurant_id)` / `menu_item (restaurant_id, id)`, so a row can never point at another restaurant's event or item; `record_support_access` / `set_event_module_unlock` require a live grant of THIS session for the event's restaurant and re-check `is_platform_admin` and the session expiry; `save_quiz_answer` accepts only the event's open question (another event's id → the same `QUIZ_CLOSED`); `set_order_pieces` filters the line by event; `guest_rsvp_state` / `quiz_guest_state` join the guest to `p_event_id`.
- `support_log` append-only trigger: refuses UPDATE/DELETE/TRUNCATE; the delete exception for a cascading restaurant delete works because the RI cascade runs after the restaurant row is gone in the same transaction; `support_log` has no FK to grant/session/account/event, so it outlives them. m10 widens `support_log_kind` and the new `module` CHECKs hold for existing rows.
- Team matrix enforced under `restaurant … for update` (`team_lock_actor`); LAST_OWNER checked under that lock; link rule (`team_account_exclusive`) and the `restaurant_member_team_links` trigger delete team-issued unused links on a second membership while CLI (`created_by null`) and admin links stay.

**Concurrency / locks:**
- Order is consistent wherever two locks are taken: `reset_event` 3003→3008→(3013)→event row FOR UPDATE; `purge_event_guest_data` 3003→3008→event row (see finding 1 for 3013); `apply_venue_template` (3003, event)→(3003, template) and nothing takes template→event (`create_venue_template` and `create_event_from_template` take one lock each). No function takes a guest/run row lock and then the event row, so the "row then advisory" direction never occurs.
- FOR SHARE windows: `save_guest_guess*` (event, before the upsert), `save_guest_rsvp` (event; `close_event_rsvp`'s UPDATE waits for in-flight saves and later saves see the new deadline), `save_quiz_answer` (run row; `close` takes it FOR UPDATE, so an answer never lands after a committed close; the close's `quiz_question` UPDATE is NO KEY UPDATE and does not conflict with the answers' KEY SHARE). `set_order_pieces` locks the line FOR UPDATE. `add_event_waiter`, `set_event_menu`, `set_event_rsvp_options`, `set_event_module_unlock` lock the event row FOR UPDATE. `begin_login_attempt` serializes per key with `(3010, hashtext(key))`. `claim_retention_sweep`'s UPDATE is race-safe under READ COMMITTED re-evaluation. `add_restaurant_owner`/`add_restaurant_member`'s `insert … on conflict (email) do nothing returning … into` + `found` correctly distinguishes created vs existing under a race.
- Triggers: `guest_rsvp_absence_by_organizer` is an AFTER ROW trigger, so inside `save_guest_rsvp` it fires at the end of the `update guest` statement and the following upsert overwrites `answered_by` — the author is preserved as documented. `support_log_append_only` TRUNCATE path never dereferences `old`.

**Cascades (nothing cascades more than intended):** `event.restaurant_id` has no cascade (documented); `menu_item` delete → `event_menu_item`/`event_rsvp_option` rows go, `order_item.menu_item_id` and `guest_rsvp.menu_item_id` set null (documented: the line and the answer stay); `quiz_answer`/`quiz_score`/`guest_rsvp` cascade with the guest, so `purge`/`reset guests` take them; `event_waiter` cascades with the event; `support_grant` cascades with session/account/restaurant; `support_log` only with the restaurant. `purge` deletes only guest data (guests, groups, snapshots, spotlight, waiters, order notes) and keeps the event row, venue, questions, lines, drinks, menu, brand; never a template (`not e.is_template`), never inside the term (re-checked under the row lock); DELETE only — no `TRUNCATE … RESTART IDENTITY` anywhere, snapshot/spotlight/revision ids keep growing.

**`reset_counts` / `reset_event` latest versions (pub-quiz):** same signatures as m1, ACL kept, `quiz` part added and implied by `guests`, deletes dependents first, counts `quizAnswers`/`quizAsked`; the TS schema (`src/lib/reset/api.ts:39-40`) carries both keys — CLAUDE.md's note that the OLD code's strict schema refuses them until the code ships right after the migration is accurate.
