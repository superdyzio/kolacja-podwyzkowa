# Rules for AI

This file provides guidance to AI Agent when working with code in this repository.

## Project rules

- Commit subject format: `[<model>] <message>` (e.g. `[Opus 5.5] feat(<change-id>): <phase title> (p<N>)`). Never add a `Co-Authored-By` trailer.
- Source of truth: `context/foundation/` (`prd-v2.md` — current product, M-2 restaurant platform; `prd.md` — v1, details of the preserved FR-001..FR-020; `roadmap.md`, `tech-stack.md`, `shape-notes.md`; `m2-product-notes.md` holds design notes and loses to `prd-v2.md`). Changes live in `context/changes/<change-id>/`.
- Unattended (overnight) runs follow `context/foundation/overnight-brief.md` and log decisions, added dependencies and blockers in `context/foundation/overnight-log.md`.
- UI language: Polish AND English (i18n). Every user-facing text (pages, errors, API messages, confirms, aria labels) exists in both, through the `{ pl, en }` dictionaries described under "Languages"; never hard-code a UI string in one language only. Polish is the default; the restaurant page starts in English.

## Architecture

**Astro 7 SSR app** with React 19 islands, Tailwind 4, Supabase (Postgres only) and shadcn/ui components. Runs as a Node standalone server (`@astrojs/node`), deployed to AWS Lambda.

### Rendering mode

Full server-side rendering (`output: "server"` in astro.config.mjs). All pages are server-rendered by default. API routes must export `const prerender = false`.

Behind a proxy: `security.allowedDomains: [{ protocol: "https" }]` makes Astro trust `X-Forwarded-Proto: https` (and `X-Forwarded-Host`). On AWS Lambda the Function URL terminates TLS and the Lambda Web Adapter forwards to the Node server over plain http with the original `Host` and `X-Forwarded-Proto: https`, so `Astro.url` is the public `https://…` URL — guest links and QR cards come out as https, and Astro's origin check (on by default; it refuses body-less or form POST/PATCH/DELETE whose `Origin` differs from `Astro.url.origin`) keeps working. Locally nothing sends these headers and `Astro.url` is what was requested (`http://localhost:4321`, `http://<LAN IP>:4321`). The smoke checks both (links/cards via a proxy, same-origin vs foreign POST).

### Languages (i18n)

- `src/lib/i18n/` (pure): `Locale` = `"pl" | "en"`, `defineMessages(pl, en)` → `(locale = "pl") => dictionary` (`en` is type-checked against the shape of `pl`, entries may be functions), `pluralPl` / `pluralEn` (`plural.ts`), `resolveLocale`, `localeCookieName`, `defaultLocaleFor`.
- The middleware sets `locals.locale` for EVERY request (pages and API): the cookie of the path's area — `kp-lang-r` for `/r/` and `/api/r/`, `kp-lang` for everything else, so the organizer's choice never flips the restaurant's tablet — else the default by path prefix (`/r/` → `en`, the rest → `pl`). Never by the key: denials stay identical for every reason (the 404 rewrite keeps the original path's locale). A page GET with `?lang=pl|en` sets that cookie (1 year, HttpOnly, SameSite=Lax) and 303-redirects to the address without it.
- `Layout.astro` renders `<html lang>` and the PL/EN switch (`LanguageSwitch.astro`, query-only links `?lang=en`, so a page never echoes its own path); `languageSwitch={false}` on the TV and the print sheet.
- Texts live per domain in `src/lib/<domain>/messages.ts` (`xxxMessages = defineMessages({…}, {…})`); pure text builders take a trailing `locale: Locale = "pl"`. Islands get a required `locale` prop from the page (`Astro.locals.locale`) and pass it down; API routes answer in `locals.locale` (`readJsonBody(request, schema, locals.locale)`, `httpMessages`, `noAccessMessages`, `networkFailure(locale)` / `toFailure(data, locale)` in islands).
- Not translated: DB content (event, guest, room, table and dish names, notes, the questions incl. the starter base), URL slugs, money format (`formatAmount` „1 499,99 zł” in both). AI topics are generated in the requester's language.

### Access model (link keys and staff accounts)

Two independent kinds of access: link keys for one event (below) and staff accounts with a session cookie for the restaurant panel (staff-accounts, after this list). A session never opens a key route and a key never opens the panel.

Identity is an unguessable key in the URL path (PRD Access Control, NFR-009): organizer `/o/<key>`, TV `/tv/<key>` (read-only), guest `/g/<key>` (personal link, S-05), restaurant `/r/<key>` (read-only, restaurant-orders). Keys: 18 random bytes, base64url, 24 chars, unique across ALL events (multi-tenant-events): a key resolves to exactly one event, and `access.event.id` is the only event a route may read or write (NFR-012).

- `src/lib/access/` — `keys.ts` (`generateAccessKey`, `isWellFormedAccessKey`), `paths.ts` (`parseAccessPath`, `organizerPath`, `tvPath`, `guestPath`), `resolve.ts` (`resolveAccess`, `decideAccess`, `accessFor`, types `Access`, `OrganizerAccess`, `TvAccess`, `GuestAccess`), `messages.ts` (the shared no-access texts). Import from `@/lib/access`.
- `src/middleware.ts` guards every path under `/o/`, `/tv/`, `/g/`, `/r/` and `/api/{o,tv,g,r}/`. A valid key of the matching role sets `Astro.locals.access` and adds `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag`. Anything else gets the same 404: the `NoAccess` page (`src/components/NoAccess.astro`, also `src/pages/404.astro`) or `{"error":"Brak dostępu"}` for API routes. DB errors throw → `src/pages/500.astro`, never a 404.
- New guarded routes go under those prefixes, e.g. `src/pages/o/[key]/goscie.astro` or `src/pages/api/o/[key]/guests.ts`. Inside, re-check with `accessFor(Astro.locals, "organizer")` (or `context.locals`) and answer 404 when it is null.
- Astro pages: do not `return` from the frontmatter (ESLint `no-misused-promises` crashes on it). Set `Astro.response.status = 404` and render `<NoAccess />` instead.
- `TvAccess`, `GuestAccess` and `RestaurantAccess` carry no keys; never add organizer-only data (keys, guesses, ranking, drafts) to TV or guest responses, and never another guest's data to a guest response — with ONE exception (the published seating): the names and seat numbers of the latest published snapshot, exactly what the TV shows (`seat.tablemates` at the guest's OWN table, and since guest-venue-names `drawing.tables[].seats` at every table), never ids, keys, absence flags or anything outside that snapshot. The order (guest-delivered) adds the guest's OWN order lines and the lines for the middle of their table in that snapshot (dish, note, quantity, which pieces arrived and whether „you”, „a guest” or „the organizer” marked them) — never prices, a tablemate's personal dishes or anyone's id; the one internal id a phone gets is `lineId` (the handle for marking a piece, re-checked in `set_order_pieces` under the row lock; a foreign or unknown line gives the same 409).
- Restaurant access (restaurant-orders): the key is `event.restaurant_key` (DB default like guest keys, unique, distinct from the organizer/TV keys; `OrganizerAccess.event.restaurantKey` carries it, but since client-restaurant-split the client's pages no longer show it: the tablet link is the venue's, on the panel's event card). Always on; „Wymień link” (`rotateEventKey(…, "restaurant")` on the panel's event card) writes a fresh key and the old link is dead at once. The restaurant sees guest names (the published seating, like the TV, plus whose dishes go where) but never prices, ids, keys, absences, the drinks on the bill (bill-drinks) or anything else organizer-only. Routes `src/pages/api/r/[key]/…` start with `const api = restaurantApi(locals); if (api instanceof Response) return api;` (`src/lib/restaurant-api.ts`). A restaurant key never opens `/o/`, `/tv/`, `/g/` and their APIs, and vice versa.
- Guest access (S-05): `resolveAccess(db, "guest", key)` = ONE query (guest by `access_key` with `event(id, name, guest_access_enabled)` embedded) → `GuestAccess { role: "guest", event: { id, name }, guest: { id, displayName } }` only while the organizer's switch `event.guest_access_enabled` is on (default OFF). Switch off, revoked, unknown, malformed and other roles' keys all get the identical denial (the smoke compares the bodies); a guest key never opens `/o/…`, `/tv/…`, `/api/o/…`, `/api/tv/…`.
- Guest API routes (`src/pages/api/g/[key]/…`, S-06..S-08 too) start with `const api = guestApi(locals); if (api instanceof Response) return api;` (`src/lib/guest-api.ts`, mirrors `organizerApi`). The current guest is `api.access.guest.id` — never take a guest id from the body, query or params.
- Staff accounts (staff-accounts, F-03; migration `20261109140000_staff_accounts.sql`, `src/lib/auth/` — pure `tokens.ts`, `password.ts`, `email.ts`, `limits.ts`, `cookie.ts`, `paths.ts`, `origin.ts`, `messages.ts`, `forms.ts`, `types.ts`; DB `service.ts`; import from `@/lib/auth`; product name `PRODUCT_NAME` „Stolik” in `src/lib/i18n/product.ts`):
  - Tables (RLS on, revoked from `anon`/`authenticated`): `staff_account` (`email` lowercase unique, `display_name`, `password_hash` null until the person sets one, `is_platform_admin`, `password_changed_at`), `restaurant_member` (`restaurant_id`, `account_id`, `role` `owner | manager | waiter`, PK the pair; cascades with both), `staff_session` (`token_hash`, `expires_at`), `staff_token` (`kind` `invite | reset`, `token_hash`, `expires_at`, `used_at`, `created_by`; TWO FKs to `staff_account`, so an embed needs the hint `staff_account!staff_token_account_id_fkey`), `login_attempt` (`key_hash`, `created_at`). Login throttle per e-mail (never per IP: no trusted client IP behind the Function URL): 10 attempts in 15 minutes (`LOGIN_FAILURE_LIMIT`, `LOGIN_WINDOW_SECONDS`), a success clears it, an existing session is unaffected; the password change goes through the same throttle.

Results are status unions.

It sets `Astro.locals.staff: StaffSession | null` (`App.Locals.staff`, null on every other path) and clears a session cookie that opens nothing on its own answers. Every mutation under `/api/panel/` and `/api/auth/` without the page's own `Origin` → 403 before any DB read. Staff areas answer with `AUTH_AREA_HEADERS`: `no-store`, `X-Robots-Tag`, `X-Frame-Options: DENY` and `Referrer-Policy: same-origin` — NOT `no-referrer`: a plain HTML form post from a `no-referrer` page sends `Origin: null`, which Astro's origin check and ours refuse.

Platform-admin-only routes start with `panelPlatformApi(locals)` (anyone else: `denied(locals)`, the same 404); panel PAGES take their restaurant through `findPanelRestaurant(locals, Astro.params.id, roles?)` and their event through `findPanelEvent(locals, Astro.params.id, roles?)` (`panelEventApi` uses it too, so pages and routes decide alike; null → `Astro.response.status = 404` + `<NoAccess />`). A restaurant switched off by the platform admin (platform-restaurants) gives the 404 / null in every one of these guards at once. - Draw and restore (S-04), `src/lib/seating/` (pure `neighbours.ts`, `draft.ts`, `draw.ts`; DB in `service.ts`):
  - The draw runs in the organizer's BROWSER (`drawSeating(input, historyPairs, { random, timeBudgetMs?, maxIterations?, now? })` in `useSeatingBoard.draw()`; keeps server requests short). Inputs: a fresh board (`GET /seating`) and the neighbour history (`GET /seating/history`). Hard rules: every PRESENT non-pinned guest gets exactly one free existing seat; pinned rows never move (a pinned ABSENT guest keeps the seat, which shows empty on the TV); non-pinned absent guests get no seat; each group's present members (≥ 2) sit at one table on seats forming one block of side neighbours (`areConsecutiveSeats`: round = an arc with wrap-around, rectangular = a run on ONE side, opposite never joins); pinned group members fix the table and the rest must join their block; the draw's own rule (draw-neighbour, NOT re-checked by `validateDraft`, so manual edits and restores may break it): nobody sits alone — every present seated guest, pinned ones included, has at least one `neighbours()` seat (side or opposite) held by a present guest (an absent pinned guest's seat is no company). Soft rule: minimise repeated neighbour pairs (`neighbours()` = side ∪ opposite between two occupied seats; pairs from the same current group are excluded). Infeasible (`too-many-guests`, `group-too-large`, `pinned-group-split`, `pinned-group-no-room`, `groups-do-not-fit`, `lonely` with the names) → `seatingMessages(locale)` infeasible text + `describeDrawProblem` lines, nothing is sent.
  - Solver: mulberry32 (`createRandom(seed)`, `randomSeed()`), static feasibility checks, randomised backtracking placement of groups (forward checking; 50 000 nodes, then up to 7 fresh random restarts of 10 000 nodes when it only gave up, within half the budget — the real venue's couples hit an unlucky first search in ~0.05 % of draws; static `lonely` refusals before the search: the only present guest, a pinned guest whose every neighbour seat is pinned with nobody present; the search is skipped when no move exists), singles shuffled, then local search with annealing (single swap/move, group relocate/permute) on an incremental cost = repeats + a weight above the edge count per lonely guest (counted over the changed seats and their neighbours); after the search the best arrangement is measured again and refused as `lonely` if anyone is still alone; stops with nobody alone and 0 repeats, `maxIterations` or the budget (`DEFAULT_DRAW_BUDGET_MS` = 1200, clock read every 256 iterations). Each draw has a new seed, so a redraw differs. Tests pass a seed and `maxIterations`, never a clock.
  - History = union of guest pairs over ALL published snapshots (`getNeighbourHistory` → `NeighbourHistoryDto { snapshotCount, pairs }`), computed with each snapshot's own shape and seat count; deleted guests skipped; snapshot tables/seats read in pages of 1000 (PostgREST `max_rows`). `repeatedNeighbours(board, pairs)` drives the stats (present seated guests only).
  - Saving a draft: `POST /api/o/<key>/seating/draft { seats: [{ guestId, tableId, seat }] }` (≤ 200 rows) → `saveDraft`: `validateDraft` re-checks the hard rules against the current data (409 stale-draft message + `problems`), then DB function `replace_seating(p_event_id, p_seats jsonb)` (lock `(3003, event)`, venue tables locked `for share`) deletes every NON-pinned `seat_assignment` row and inserts the draft in one transaction (constraint failure → 409, nothing changed). 200 with the board. The draft is only the working arrangement: TV and phones (S-05) keep the latest snapshot until `POST /seating/publish`, which is unchanged.
  - Restore: `POST /seating/restore { snapshotId }` → `restoreSnapshot` (`restoreSeats`: skips deleted guests/tables, seats above today's `seat_count`, seats of current pinned rows, guests now absent; keeps pinned rows) → 200 `{ ...board, notice }` (`describeRestore` names who has no seat) / 404 snapshot-not-found message / 409. „Odrzuć zmiany” restores the latest snapshot, „Wróć do poprzedniego rozkładu” the `previous` one; the organizer publishes it afterwards. `GET /seating/history` → `NeighbourHistoryDto`. All three are organizer-only (TV key → 404).
  - UI: `DrawPanel` under the publish bar („Wylosuj projekt” / „Losuj ponownie”, repeat stats, history count, discard, back to previous). Draw/restore ask `window.confirm` only when they would replace unpublished changes that are not an untouched draw (`origin !== "draw"`). After a publish (201) the hook refetches the history.

### Key conventions

- **Path alias**: `@/*` maps to `./src/*` (tsconfig paths; mirrored in `vitest.config.ts`).
- **Astro components** for static content/layout; **React components** only when interactivity is needed.
- **Tailwind class merging**: use the `cn()` helper from `@/lib/utils` (clsx + tailwind-merge) for conditional/merged class names. Do not concatenate class strings manually.
- **shadcn/ui**: components live in `src/components/ui/`, "new-york" style variant. Install new ones with `npx shadcn@latest add [name]`.
- **API routes**: use uppercase `GET`, `POST` exports; validate input with zod.
- **Supabase migrations**: `supabase/migrations/` using naming format `YYYYMMDDHHmmss_short_description.sql`. Every new table: `enable row level security`, no policies for `anon`/`authenticated`, and `revoke all on table ... from anon, authenticated` (Supabase grants them by default).
- **React**: no Next.js directives ("use client" etc.). Extract hooks to `src/components/hooks/`.
- **Services/helpers** go in `src/lib/` (or `src/lib/services/` for extracted business logic).
- **Shared types** (entities, DTOs) go in `src/types.ts`.

### Tests

- Unit tests next to the code: `src/**/*.test.ts`.
- DB integration tests: `tests/integration/*.test.ts`, wrapped in `describe.skipIf(!hasLocalDb)` from `tests/integration/helpers.ts`. They run only when `SUPABASE_URL` points at `127.0.0.1`/`localhost`. Files run sequentially (`fileParallelism: false`).
- Integration tests never use an existing event: each file creates its own restaurant + event in `beforeAll` (`createTestEvent(db, label)` in `tests/integration/helpers.ts`) and deletes both in `afterAll` (`releaseTestEvent`); helpers take the event id. `isolation.test.ts` proves two events cannot reach each other's rows through any service or DB function.
- HTTP-level behaviour (status codes, headers, page bodies) is checked by `npm run smoke` against the production preview.

- Deploy (decided by the user on 2026-10-30; README „Wdrożenie na AWS”): one AWS Lambda function `kolacja-podwyzkowa` (arm64, `nodejs24.x`, 1024 MB, 30 s, handler `run.sh`) behind a Function URL (auth NONE; the link keys do access control), with the AWS Lambda Web Adapter layer v1.1.0 (`arn:aws:lambda:<region>:753240598075:layer:LambdaAdapterLayerArm64:30`, `AWS_LAMBDA_EXEC_WRAPPER=/opt/bootstrap`, readiness check `/favicon.png`) forwarding to the Node server on port 8080; a hosted Supabase Free project in the same region. ## CI

GitHub Actions workflow (`.github/workflows/ci.yml`) on every push and PR to `main`:

- `ci` — lint, `astro check`, `npm test` (DB integration tests skip) and build. Optional repository secrets `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.
