# Rules for AI

This file provides guidance to AI Agent when working with code in this repository.

## Project rules

- Commit subject format: `[<model>] <message>` (e.g. `[Opus 5.5] feat(<change-id>): <phase title> (p<N>)`). Never add a `Co-Authored-By` trailer.
- Source of truth: `context/foundation/` (`prd-v2.md` — current product, M-2 restaurant platform; `prd.md` — v1, details of the preserved FR-001..FR-020; `roadmap.md`, `tech-stack.md`, `shape-notes.md`; `m2-product-notes.md` holds design notes and loses to `prd-v2.md`). Changes live in `context/changes/<change-id>/`.
- Unattended (overnight) runs follow `context/foundation/overnight-brief.md` and log decisions, added dependencies and blockers in `context/foundation/overnight-log.md`.
- UI language: Polish AND English (i18n). Every user-facing text (pages, errors, API messages, confirms, aria labels) exists in both, through the `{ pl, en }` dictionaries described under "Languages"; never hard-code a UI string in one language only. Polish is the default; the restaurant page starts in English.

## Commands

- `npm run dev` — start dev server (Node; reads `.env` through Vite)
- `npm run build` — production build (SSR via `@astrojs/node` standalone; every server dependency is bundled into `dist/server`, see `bundleServerDependencies` in `astro.config.mjs`); secrets are never inlined, they are read from the process env at runtime
- `npm run preview` — run the production build on http://localhost:4321 with `.env` loaded (`node --env-file-if-exists=.env … astro preview`; Astro 7 runs it detached when an agent starts it; stop it with `npx astro preview stop`). After changing `.env`, restart the preview (no rebuild needed)
- `npm test` — Vitest unit + integration tests (`vitest run`); `npm run test:watch` for watch mode
- `npm run lint` — ESLint with type-checked rules; `npm run lint:fix` to auto-fix
- `npx astro check` — type check (run `npx astro sync` first after changing the env schema)
- `npm run format` — Prettier (includes prettier-plugin-astro + prettier-plugin-tailwindcss)
- `npm run env:local` — write `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` for the local Supabase into `.env` (keeps the other lines)
- `npm run event:create` — `npm run event:create -- [--restaurant "<name>" | --restaurant-id <id>] [--name "<event name>"]`: create an event (with the new-event module defaults: AI topics and the guessing game off, event-modules) (with a new restaurant unless `--restaurant-id` names one; defaults „Restauracja” / „Wydarzenie”) with the starter question base in the database of `.env`, print the host first, then its links (`BASE_URL` for the link origin). The only way to start an event until the restaurant panel (S-11); `scripts/create-event.mjs` + `scripts/lib/platform.mjs`
- `npm run links` — print every event (restaurant · event name, id) with its organizer, TV and restaurant links (recovery for a lost organizer link)
- `npm run platform:admin` — `npm run platform:admin -- <email> [--name "<name>"] [--remote]`: create (or find) a platform administrator's staff account in the database of `.env` (or the `SUPABASE_*` given on the command line; prints the host first; a non-local DB needs `--remote`) and print a one-time link `/haslo/<token>` (`BASE_URL` for the origin): an invitation (7 days) for an account without a password, a reset link (24 h) for one with a password — also the way back in for an admin who lost it; every run replaces the account's earlier unused links (`scripts/platform-admin.mjs`)
- `npm run retention` — `npm run retention -- [--dry-run] [--restaurant-id <id>] [--limit <n>] [--remote]`: delete the guests' data of every event past its restaurant's retention term (privacy-retention, S-26; the same DB functions the app runs before serving an expired event and on panel page views) in the database of `.env` (prints the host first; a non-local DB needs `--remote`, and there the run stops — exit 1, nothing deleted — unless this machine's clock agrees with the server's HTTP `Date` header within 5 minutes (`MAX_CLOCK_SKEW_MS`, pure `clockSkewMs` / `clockSkewProblem`, `tests/scripts/retention-clock.test.ts`): `purge_event_guest_data` decides the term by the time the script sends as `p_now`); `--dry-run` only lists them (`scripts/retention.mjs`, `purgeExpiredGuestData` in `scripts/lib/platform.mjs`). There is NO scheduler (cron, EventBridge, pg_cron): scheduling this command is the user's later infrastructure decision
- `npm run package:lambda` — build into `dist-lambda/build` (never touches `dist/`) and pack `dist-lambda/function.zip` for AWS Lambda (`run.sh` + `server/` + `client/`, no `node_modules`); fails on env files or secret values from `.env`/`.env.aws`/`.dev.vars` in the package, native modules not for linux-arm64, a zip ≥ 50 MB, and unless the unpacked zip (in a read-only temp dir outside the repo, like `/var/task`) loads every server module and answers HTTP through `run.sh`
- `npm run deploy:aws` — `AWS_REGION=<region> npm run deploy:aws [-- --dry-run]`: packages, then creates or updates in place (never deletes) the IAM role, the Lambda function, its Function URL with public permissions and the log group through the `aws` CLI (profile `AWS_PROFILE`, default `mikusia`); config and secrets from `.env.aws`. ## Architecture

**Astro 7 SSR app** with React 19 islands, Tailwind 4, Supabase (Postgres only) and shadcn/ui components. Runs as a Node standalone server (`@astrojs/node`), deployed to AWS Lambda.

### Rendering mode

Full server-side rendering (`output: "server"` in astro.config.mjs). All pages are server-rendered by default. API routes must export `const prerender = false`.

Behind a proxy: `security.allowedDomains: [{ protocol: "https" }]` makes Astro trust `X-Forwarded-Proto: https` (and `X-Forwarded-Host`). On AWS Lambda the Function URL terminates TLS and the Lambda Web Adapter forwards to the Node server over plain http with the original `Host` and `X-Forwarded-Proto: https`, so `Astro.url` is the public `https://…` URL — guest links and QR cards come out as https, and Astro's origin check (on by default; it refuses body-less or form POST/PATCH/DELETE whose `Origin` differs from `Astro.url.origin`) keeps working. Locally nothing sends these headers and `Astro.url` is what was requested (`http://localhost:4321`, `http://<LAN IP>:4321`). The smoke checks both (links/cards via a proxy, same-origin vs foreign POST).

### Languages (i18n)

- `src/lib/i18n/` (pure): `Locale` = `"pl" | "en"`, `defineMessages(pl, en)` → `(locale = "pl") => dictionary` (`en` is type-checked against the shape of `pl`, entries may be functions), `pluralPl` / `pluralEn` (`plural.ts`), `resolveLocale`, `localeCookieName`, `defaultLocaleFor`.
- The middleware sets `locals.locale` for EVERY request (pages and API): the cookie of the path's area — `kp-lang-r` for `/r/` and `/api/r/`, `kp-lang` for everything else, so the organizer's choice never flips the restaurant's tablet — else the default by path prefix (`/r/` → `en`, the rest → `pl`). Never by the key: denials stay identical for every reason (the 404 rewrite keeps the original path's locale). A page GET with `?lang=pl|en` sets that cookie (1 year = `LOCALE_COOKIE_MAX_AGE_SECONDS`, HttpOnly, SameSite=Lax) and 303-redirects to the address without it, always a same-origin path (`localeSwitchTarget` collapses leading slashes and backslashes: `//evil.com/?lang=pl` → `/evil.com/`).
- `Layout.astro` renders `<html lang>` and the PL/EN switch (`LanguageSwitch.astro`, query-only links `?lang=en`, so a page never echoes its own path); `languageSwitch={false}` on the TV and the print sheet.
- Texts live per domain in `src/lib/<domain>/messages.ts` (`xxxMessages = defineMessages({…}, {…})`); pure text builders take a trailing `locale: Locale = "pl"`. Islands get a required `locale` prop from the page (`Astro.locals.locale`) and pass it down; API routes answer in `locals.locale` (`readJsonBody(request, schema, locals.locale)`, `httpMessages`, `noAccessMessages`, `networkFailure(locale)` / `toFailure(data, locale)` in islands).
- Not translated: DB content (event, guest, room, table and dish names, notes, the questions incl. the starter base), URL slugs, money format (`formatAmount` „1 499,99 zł” in both). AI topics are generated in the requester's language.

### Access model (link keys and staff accounts)

Three independent kinds of access: link keys for one event (below), staff accounts with a session cookie for the restaurant panel (staff-accounts, after this list) and the per-event waiter's own cookie for one event's floor (event-waiter-access, under „The floor”). A session never opens a key route, a key never opens the panel, and neither cookie ever opens the other's area.

Identity is an unguessable key in the URL path (PRD Access Control, NFR-009): organizer `/o/<key>`, TV `/tv/<key>` (read-only), guest `/g/<key>` (personal link, S-05), restaurant `/r/<key>` (read-only, restaurant-orders). Keys: 18 random bytes, base64url, 24 chars, unique across ALL events (multi-tenant-events): a key resolves to exactly one event, and `access.event.id` is the only event a route may read or write (NFR-012).

Hard rules: every PRESENT non-pinned guest gets exactly one free existing seat; pinned rows never move (a pinned ABSENT guest keeps the seat, which shows empty on the TV); non-pinned absent guests get no seat; each group's present members (≥ 2) sit at one table on seats forming one block of side neighbours (`areConsecutiveSeats`: round = an arc with wrap-around, rectangular = a run on ONE side, opposite never joins); pinned group members fix the table and the rest must join their block; the draw's own rule (draw-neighbour, NOT re-checked by `validateDraft`, so manual edits and restores may break it): nobody sits alone — every present seated guest, pinned ones included, has at least one `neighbours()` seat (side or opposite) held by a present guest (an absent pinned guest's seat is no company). Soft rule: minimise repeated neighbour pairs (`neighbours()` = side ∪ opposite between two occupied seats; pairs from the same current group are excluded). Infeasible (`too-many-guests`, `group-too-large`, `pinned-group-split`, `pinned-group-no-room`, `groups-do-not-fit`, `lonely` with the names) → `seatingMessages(locale)` infeasible text + `describeDrawProblem` lines, nothing is sent.
  - Solver: mulberry32 (`createRandom(seed)`, `randomSeed()`), static feasibility checks, randomised backtracking placement of groups (forward checking; 50 000 nodes, then up to 7 fresh random restarts of 10 000 nodes when it only gave up, within half the budget — the real venue's couples hit an unlucky first search in ~0.05 % of draws; static `lonely` refusals before the search: the only present guest, a pinned guest whose every neighbour seat is pinned with nobody present; the search is skipped when no move exists), singles shuffled, then local search with annealing (single swap/move, group relocate/permute) on an incremental cost = repeats + a weight above the edge count per lonely guest (counted over the changed seats and their neighbours); after the search the best arrangement is measured again and refused as `lonely` if anyone is still alone; stops with nobody alone and 0 repeats, `maxIterations` or the budget (`DEFAULT_DRAW_BUDGET_MS` = 1200, clock read every 256 iterations; scale-150 measured 0–6 ms at 150 guests / 60 tables / 30-seat tables, the full budget only when repeats cannot be avoided — `src/lib/seating/draw-scale.test.ts`, benchmark with `DRAW_BENCH=1`). Each draw has a new seed, so a redraw differs. Tests pass a seed and `maxIterations`, never a clock.
  - History = union of guest pairs over ALL published snapshots (`getNeighbourHistory` → `NeighbourHistoryDto { snapshotCount, pairs }`), computed with each snapshot's own shape and seat count; deleted guests skipped; snapshot tables/seats read in pages of 1000 (PostgREST `max_rows`). `repeatedNeighbours(board, pairs)` drives the stats (present seated guests only).
  - Saving a draft: `POST /api/o/<key>/seating/draft { seats: [{ guestId, tableId, seat }] }` (≤ `MAX_GUESTS` rows) → `saveDraft`: `validateDraft` re-checks the hard rules against the current data (409 stale-draft message + `problems`), then DB function `replace_seating(p_event_id, p_seats jsonb)` (lock `(3003, event)`, venue tables locked `for share`) deletes every NON-pinned `seat_assignment` row and inserts the draft in one transaction (constraint failure → 409, nothing changed). 200 with the board.   - Restore: `POST /seating/restore { snapshotId }` → `restoreSnapshot` (`restoreSeats`: skips deleted guests/tables, seats above today's `seat_count`, seats of current pinned rows, guests now absent; keeps pinned rows) → 200 `{ ...board, notice }` (`describeRestore` names who has no seat) / 404 snapshot-not-found message / 409. „Odrzuć zmiany” restores the latest snapshot, „Wróć do poprzedniego rozkładu” the `previous` one; the organizer publishes it afterwards. `GET /seating/history` → `NeighbourHistoryDto`. ### Key conventions

- **Path alias**: `@/*` maps to `./src/*` (tsconfig paths; mirrored in `vitest.config.ts`).
- **Astro components** for static content/layout; **React components** only when interactivity is needed.
- **Tailwind class merging**: use the `cn()` helper from `@/lib/utils` (clsx + tailwind-merge) for conditional/merged class names. Do not concatenate class strings manually.
- **shadcn/ui**: components live in `src/components/ui/`, "new-york" style variant. Install new ones with `npx shadcn@latest add [name]`.
- **API routes**: use uppercase `GET`, `POST` exports; validate input with zod.
- **Supabase migrations**: `supabase/migrations/` using naming format `YYYYMMDDHHmmss_short_description.sql`. Every new table: `enable row level security`, no policies for `anon`/`authenticated`, and `revoke all on table ... from anon, authenticated` (Supabase grants them by default).
- **React**: no Next.js directives ("use client" etc.). Extract hooks to `src/components/hooks/`.
- **Services/helpers** go in `src/lib/` (or `src/lib/services/` for extracted business logic).
- **Shared types** (entities, DTOs) go in `src/types.ts`.

### Scale (scale-150, S-19; FR-033, NFR-011, NFR-015)

- Limits per event: 150 guests (`MAX_GUESTS`), tables of 2–30 seats (`MIN_SEATS`/`MAX_SEATS`), 60 tables (`MAX_TABLES`), 10 rooms (`MAX_ROOMS`), place predictions 1…150, 600 order lines; DB CHECKs mirror the seat and place ranges (migration `20261111010000_scale_150.sql`, data-preserving; deploy: the migration BEFORE the code as always — pushing it early is safe because old code keeps its stricter limits on the migrated DB, while new code on an un-migrated DB turns a 21–30-seat table or a place above 100 into a 500 at the CHECK). Templates (S-15) follow the same limits. A new limit goes into the constant AND, where one exists, the DB CHECK; tests read the constants.
- Measured locally (2026-11-10, Apple Silicon laptop, one `npm run preview` process + local Supabase in Docker): the draw at full size 0–6 ms (worst case = its 1.2 s budget); `POST /seating/publish` 12–27 ms; at full size the guest's 200 answer is ~12.7 KB (drawing of 60 tables and 150 names; far below Lambda's 6 MB) and the TV's ~10–11 KB; `npm run load:local` with 1 event (200 phones + TV, ~80 req/s): 204 p50 12 ms / p95 31 ms, 200 p50 15 ms / p95 39 ms, every poller saw the publish within 2.5 s (p50 1.3 s); 3 events publishing in the same second (603 pollers, ~246 req/s) on that ONE local process: p95 4.2 s, max 6.3 s — the single Node process and Docker are the bottleneck there, so NFR-015 is not provable locally.
- Hosting estimate (Lambda: one request per instance, instances ≈ requests/s × mean duration): one event ≈ 201 pollers / 2.5 s ≈ 80 req/s → ~1–2 instances steady; right after a publish ~200 phones take the 200 path within one poll window (~16 DB queries each: the version reads are repeated by `getGuestState`, plus 4 for `guestDrawing`) ≈ 3 200 PostgREST queries in 2.5 s per event; three events ≈ 240 req/s ≈ 4–20 instances. What binds the free tier is the request COUNT: 201 pollers × 1 440 polls/h × 3 h ≈ 870 k requests per evening against Lambda's 1 M/month (phones pause while hidden, so real numbers are lower). Check the account's Lambda concurrency quota (new accounts can start far below 1000).
- Levers if the measurement after deploy misses the target: pass the version reads into `getGuestState` (keeps the 204/200 same-reads invariant) and cache `guestDrawing` per snapshot id in the process (snapshots are immutable; ids are never reused); both cut the 200 path from ~16 to ~7 queries.
- After deploy (user, Open Question 4): with real phones open, watch CloudWatch `ConcurrentExecutions`, `Duration` p50/p95 and `Throttles` during a publish, the 200 vs 204 split of `/api/g/*/state`, the Supabase dashboard's API request rate and any 5xx/429, and time publish → phone with a stopwatch on 3–5 devices (target ≤ 5 s). `load:local` refuses remote targets on purpose.
